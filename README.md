버그가 **일부러 심어진** 작은 게임 코드 모음입니다. [C++판 BugHunt](https://github.com/gusgh0157/BugHunt)의 C# 버전이고, 엔진(유니티 등)이 아니라 **C# 언어와 .NET 런타임 자체**에서 생기는 버그를 다룹니다.

- **1부: 예외와 스택 트레이스 (랩 1~8)**: 프로그램이 예외로 죽은 순간 **호출 스택**과 **스택 트레이스**를 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 흐름 추적 (랩 9~23)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 직접 중단점을 걸고 값을 확인하며 따라갑니다. 연산자와 평가 순서(`x = x++`, `|` 와 `||`)도 여기서 다룹니다.
- **3부: 컨테이너와 컬렉션 (랩 24~30)**: 범위 밖 인덱스, `List<struct>` 복사본, 가변 키, 동시 수정, 불안정 정렬, `yield`와 지연 실행.
- **4부: C# 언어 함정 (랩 31~37)**: 소리 내어 읽으면 맞아 보이는 코드. 저장한 `GetHashCode`, `??` 우선순위, enum 범위 밖 값, struct 복사, 문자열에 `lock`, 루프 변수 캡처, 돈에 `double`.
- **5부: 인터페이스와 상속 (랩 38~45)**: `new` 와 `override`, 인터페이스 기본 구현과 명시적 구현, struct 박싱 사본, 생성자 안의 가상 호출, `Equals` 불일치, 형식 검사 순서, 배열 공변성. 조사식으로 실제 형식을 봅니다.
- **6부: 파일 입출력 (랩 46~53)**: 상대 경로, `StreamWriter` 버퍼, 공유 모드, `Path.Combine`, 인코딩과 BOM, 줄바꿈, 반쯤 쓴 파일, 기다리지 않은 비동기 쓰기. 디스크에 실제로 무엇이 있는지 확인합니다.
- **7부: 직렬화 JSON/XML (랩 54~61)**: 이름 대소문자, 저장되지 않는 필드, 다형성, 공유 참조, 없음과 null과 0, `XmlSerializer` 규칙, XML 네임스페이스, 이스케이프. 저장한 것과 불러온 것을 나란히 비교합니다.
- **8부: 비동기와 동시성 (랩 62~71)**: `async`/`await`, `Task`, 스레드, 비동기 코드의 예외 처리(`catch ... when`, `ExceptionDispatchInfo`). 병렬 스택 창과 작업 창을 씁니다.
- **9부: 리소스와 메모리 (랩 72~74, 선택)**: `Dispose`, GC, 종료자. 메모리 스냅샷과 진단 도구를 씁니다.
- **10부: unsafe와 네이티브 메모리 (랩 75~82, 선택)**: 포인터, `stackalloc`, `fixed`, `GCHandle`, 네이티브 콜백, `ArrayPool`, 구조체 레이아웃. 메모리 창으로 주소와 바이트를 봅니다.
- **11부: 멈춤 - 무한루프와 데드락 (랩 83~88)**: 죽지도 않고 끝나지도 않는 버그. **모두 중단**, 병렬 스택, 스레드 창, `dotnet-stack`/`dotnet-dump`로 멈춘 순간을 봅니다.
- **12부: 성능 - 틀리지는 않는데 느리다 (랩 89~95)**: 결과는 맞는데 느린 코드. 핫 루프의 LINQ, 문자열 `+=`, 박싱, O(n²) 탐색, 반복 생성, 예외로 흐름 제어. 성능 프로파일러와 `dotnet-counters`로 **재서** 찾습니다.
- **챌린지 (C-1~C-3, B-1~B-8)**: 1~12부를 끝낸 뒤 푸는 시험. 힌트 없이 증상 한 줄만 줍니다. 여러 단계를 거쳐 퍼지는 버그(깊은 추적)와 범주를 숨긴 버그(블라인드). [챌린지](#챌린지) 참고.

> 2026-11 재배치: 기초에서 심화 순서로 12부를 다시 짰습니다. 4부(C# 언어 함정), 5부(인터페이스와 상속), 6부(파일 입출력), 7부(직렬화)가 새로 들어가고, 비동기 이후 부는 8~12부로 밀렸습니다. 1부에 스택 오버플로 랩 8, 2부에 연산자 랩 20~23, 10부에 오버플로 랩 81~82를 더했습니다. 바로 전 번호(1~57)와 비교하면 1~7은 그대로, 8~18 → 9~19, 19~25 → 24~30, 26~35 → 62~71, 36~38 → 72~74, 39~44 → 75~80, 45~50 → 83~88, 51~57 → 89~95입니다.

어떤 버그를 어느 랩에서 다루는지는 [버그 범주별 커버리지](#버그-범주별-커버리지) 표에 모아 두었습니다. 아직 랩이 없는 대표 케이스도 "미포함"으로 적어 두었습니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 2~12부는 **직접 멈춘 곳에서부터 값을 확인하며** 추적하세요.

## 준비

필요한 것: **.NET 10 SDK**, **Visual Studio 2026** (또는 .NET 10을 지원하는 Visual Studio, ".NET 데스크톱 개발" 워크로드)

1. `BugHunt.sln`을 Visual Studio로 엽니다. (VS 2022 17.13 이상이면 `BugHunt.slnx`를 열어도 됩니다. Rider, VS Code 등 다른 IDE는 `.sln`을 쓰세요.)
   솔루션에는 채점기 프로젝트 `BugHunt.Grader`도 들어 있습니다. F5로 실행할 **시작 프로젝트는 `BugHunt`**입니다 (솔루션 탐색기에서 굵게 보이는 프로젝트).
2. 위쪽 도구 모음에서 구성을 **Debug**로 둡니다.
3. **F5**(디버깅 시작)로 실행 → 메뉴에서 랩 번호 입력.
   - 매번 같은 랩을 돌리려면: `BugHunt/Properties/launchSettings.json`의 `"commandLineArgs": ""`에 번호를 넣습니다 (예: `"1"`). 또는 솔루션 탐색기에서 BugHunt 우클릭 → 속성 → 디버그 → **디버그 시작 프로필 UI 열기** → **명령줄 인수**.
   - Ctrl+F5(디버깅하지 않고 시작)나 exe를 직접 실행하면 디버거가 붙지 않습니다. 콘솔에 스택 트레이스만 남고 끝납니다. 일부러 그렇게 보는 랩(5)도 있지만, 기본은 **F5**입니다.

명령줄에서:

```bash
dotnet run --project BugHunt -- 3
```

실행 출력(메뉴, 판정 줄)은 일본어로도 볼 수 있습니다: `dotnet run --project BugHunt -- --lang ja 3` 또는 환경 변수 `BUGHUNT_LANG=ja`. 지정하지 않으면 Windows 화면 언어가 일본어일 때 일본어, 그 밖에는 한국어입니다. 랩 소스의 주석과 힌트는 한 파일에 두 언어가 같이 있습니다(`#region 힌트 1 / ヒント 1`).

### 채점기

고친 뒤에는 채점기로 확인합니다. 저장소 폴더(이 README가 있는 곳)에서:

```bash
grade.bat
```

```bash
dotnet run --project BugHunt.Grader
```

둘은 같은 것입니다. 다른 폴더에서 `...grade.bat`을 불러도 채점기는 **자기가 들어 있는 저장소**를 채점합니다. 일부만 채점하려면 랩 번호를 붙입니다 (`grade.bat 83-88`, `grade.bat 1,5,75-82`). 챌린지는 `grade.bat C`(깊은 추적), `grade.bat B`(블라인드), `grade.bat C-1,B-3`처럼 코드로 고릅니다.

채점기(`BugHunt.Grader` 프로젝트)가 하는 일:

1. `BugHunt`를 **Debug와 Release로 새로 빌드**합니다. 빌드가 실패하면(경고도 오류입니다) 채점하지 않습니다.
2. 랩마다 `BugHunt.exe <번호>`를 **새 프로세스로** 띄웁니다. 그래서 한 랩이 죽거나(스택 오버플로, FailFast 포함) 멈춰도 다른 랩 채점에 영향이 없습니다.
3. 화면에 보이는 기본 입력으로 한 번, 그리고 **숨은 케이스**(무작위 시드로 만든 다른 입력)로 몇 번 더 돌립니다. 기대값을 코드에 박아 넣어 `[PASS]`만 맞춘 수정은 여기서 걸립니다. 숨은 케이스는 3부와 10~12부 랩, 챌린지에 있습니다 (1·2·8·9부는 기본 케이스만). 기본 케이스는 통과했는데 숨은 케이스에서 실패하면 상세 앞에 `증상은 사라졌지만 원인이 남아 있음`이 붙습니다.
4. JIT 최적화에 따라 결과가 달라질 수 있는 랩(39, 40, 42, 50, 챌린지 B-8)은 **Release로도** 돌립니다. 모든 실행이 통과해야 `PASS`입니다.
5. 콘솔에 표와 총점을, 저장소 루트에 `grade-report.json`을 남깁니다.

| 결과 | 뜻 |
|---|---|
| `PASS` | 모든 실행이 종료 코드 0, `[FAIL]` 없음, `[PASS]` 1개 이상 |
| `FAIL` | `[FAIL]`이 나왔거나 판정 출력이 없음 |
| `TIMEOUT` | 멈춤. 랩의 감시 타이머가 `[FAIL] 응답 없음`을 냈거나, 실행 한 번이 20초를 넘겨 채점기가 강제로 끝냄 |
| `CRASH` | 처리되지 않은 예외, 스택 오버플로, FailFast 등으로 프로세스가 죽음. 상세에 종료 코드가 나옵니다 |
| `SKIP` | 이 환경에서는 판정할 수 없음 (랩이 `[SKIP]`을 출력). 총점의 분모에서 빠집니다 |

처음에는 전부 `FAIL`, `CRASH`, `TIMEOUT`이 나오는 것이 정상입니다.

옵션:

| 옵션 | 뜻 |
|---|---|
| `--config Debug` / `--config Release` | 그 구성 하나로만 채점 |
| `--seed N` | 숨은 케이스 시드를 고정. 채점 결과 맨 아래에 나온 값을 넣으면 같은 입력으로 다시 채점합니다 |
| `--no-hidden` | 기본 케이스만 |
| `--no-build` | 빌드를 건너뜀 (이미 빌드된 것을 채점) |
| `--timeout MS` | 실행 한 번의 제한 시간 (기본 20000) |
| `--out 경로` | 보고서 위치 |
| `--lang ko` / `--lang ja` | 출력 언어 (기본: 환경 변수 `BUGHUNT_LANG`, 없으면 Windows 화면 언어, 그 밖에는 한국어). 판정은 언어와 상관없이 같습니다 |

숨은 케이스 하나를 디버거로 다시 보려면, 실패 상세의 `seed` 값을 명령 인수에 같이 넣습니다: `"commandLineArgs": "84 --seed 123456"`.

#### grade-report.json 형식

BugHunt 네 판(C++, C#, 언리얼, 유니티)이 같은 형식을 씁니다.

```json
{
  "edition": "cs",
  "version": "1",
  "total": 106,
  "passed": 12,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "PASS", "ms": 85, "detail": "" },
    { "id": 78, "title": "박자 콜백", "part": 10, "result": "CRASH", "ms": 152,
      "detail": "[Debug] 0x80131623 Process terminated. A callback was made on a garbage collected delegate ..." },
    { "id": 86, "title": "동시 거래", "part": 11, "result": "TIMEOUT", "ms": 2075,
      "detail": "응답 없음 (2000 ms 초과): 동시 거래" }
  ]
}
```

| 필드 | 형식 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 판 이름. 이 저장소는 `"cs"` |
| `version` | 문자열 | 보고서 **형식**의 버전 (`"1"`) |
| `total` | 정수 | 채점한 랩 수 (SKIP 포함) |
| `passed` | 정수 | `PASS` 수 |
| `labs[].id` | 정수 | 랩 번호. 챌린지는 `C-n`이 `100+n`, `B-n`이 `200+n` (예: C-1은 101, B-3은 203) |
| `labs[].title` | 문자열 | 랩 이름. `--lang`으로 고른 언어 |
| `labs[].part` | 정수 | 부 번호 (1~12). 챌린지는 `0` |
| `labs[].result` | 문자열 | `PASS`, `FAIL`, `TIMEOUT`, `CRASH`, `SKIP` 중 하나 |
| `labs[].ms` | 정수 | 걸린 시간 (그 랩의 모든 실행을 합친 밀리초) |
| `labs[].detail` | 문자열 | 실패 이유 한 줄. `PASS`면 빈 문자열. 숨은 케이스나 Release에서 실패했으면 앞에 `[Release, 숨은 케이스 seed N]`처럼 붙음. 숨은 케이스에서만 실패했으면 그 앞에 `증상은 사라졌지만 원인이 남아 있음`이 더 붙음. 이 문구도 고른 언어를 따름 |

파일은 UTF-8(BOM 없음)이고 채점기의 종료 코드는 만점이면 0, 아니면 1, 빌드 실패 등으로 채점을 못 하면 2, `--lang ja`에서 일본어 번역이 빠진 출력 줄이 있으면 3(빠진 줄을 끝에 보여 줌)입니다. 키 이름과 `result` 값은 언어와 상관없이 같습니다. CI에서 쓸 수 있습니다.

### 경고 정책

`BugHunt.csproj`는 **경고를 오류로 취급**합니다(`TreatWarningsAsErrors`). 그래서 빌드는 항상 경고 0개입니다.
그런데 현실의 코드처럼, 이 저장소에도 누군가 경고를 **꺼 두거나 눌러 둔** 곳이 있습니다 (`!`, `_ =`, `NoWarn`). 그 자리가 버그의 단서인 랩도 있습니다. 빌드 출력이 깨끗하다고 코드가 안전한 것은 아닙니다.

# 1부: 예외와 스택 트레이스

## 호출 스택과 스택 트레이스

함수가 함수를 부르면, 런타임은 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.
예외가 던져지면 .NET은 그 순간의 호출 스택을 문자열로 찍어 예외 안에 넣어 둡니다. 그것이 **스택 트레이스(StackTrace)**입니다.

디버거 없이(Ctrl+F5) 랩 1을 실행하면 콘솔에 이렇게 남습니다.

```
Unhandled exception. System.NullReferenceException: Object reference not set to an instance of an object.
   at BugHunt.Lab01.PrintPlayer(Player player) in F:\...\Lab01_Profile.cs:line 34    ← 맨 위: 예외가 난 곳
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41      ← PrintPlayer를 부른 곳
   at BugHunt.Lab01.OpenFriendList() in F:\...\Lab01_Profile.cs:line 48
   at BugHunt.Lab01.Run() in F:\...\Lab01_Profile.cs:line 53
   at BugHunt.Program.Main(String[] args) in F:\...\Program.cs:line 237               ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

스택 트레이스의 한 줄은 이렇게 생겼습니다.

```
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41
      └ 네임스페이스.클래스.메서드 ┘└ 매개변수 ┘    └──── 소스 파일 ────┘      └ 줄 ┘
```

자주 보이는 이상한 이름들:

| 스택에 보이는 이름 | 뜻 |
|---|---|
| `get_Gold`, `set_Gold` | `Gold` 속성의 get/set 접근자 |
| `<Run>b__0_0`, `<BindHotkeys>b__3_0` | 람다 (괄호 안이 람다를 품은 메서드) |
| `<>c__DisplayClass3_0` | 람다가 캡처한 변수를 담는 컴파일러 생성 클래스 |
| `<SaveAsync>d__1.MoveNext()` | async 메서드의 상태 기계. `MoveNext`가 메서드 본문입니다 |
| `--- End of stack trace from previous location ---` | 예외가 다른 곳(다른 스레드, await)에서 다시 던져진 경계 |
| `Repeat 12345 times:` | 같은 프레임이 반복됨. 스택 오버플로일 때 런타임이 접어서 보여 줍니다 |

## 디버거 창 사용법

| 하고 싶은 것 | 방법 |
|---|---|
| 호출 스택 창 | 디버깅 중 **Ctrl+Alt+C** |
| 지역 창 | **Alt+4** |
| 다른 프레임으로 이동 | 호출 스택 창에서 줄을 **더블클릭** → 코드 창이 그 함수의 "호출한 줄"(초록 화살표)로 이동하고, 지역 창이 **그 함수의 변수**로 바뀜 |
| 예외 도우미 | 예외로 멈췄을 때 뜨는 말풍선. **세부 정보 보기**, **내부 예외 보기**, "`player`이(가) null"처럼 원인 변수까지 알려 줌 |
| 지금 예외 객체 보기 | 조사식/즉시 창에 **`$exception`** |
| 예외 설정 창 | **Ctrl+Alt+E**. `Common Language Runtime Exceptions` 아래 예외를 체크하면 **처음 던져진 순간(first chance)** 멈춤. 누가 catch 하든 상관없이 |
| 외부 코드 보기 | 호출 스택 창 우클릭 → **외부 코드 표시** |
| 내 코드만 | 도구 → 옵션 → 디버깅 → 일반 → **내 코드만 사용**. 켜져 있으면(기본) .NET 내부 프레임이 `[외부 코드]` 한 줄로 접히고, 예외도 "내 코드에서 처리되지 않은" 순간에 멈춤 |

## 디버거가 멈추는 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| 예외 도우미: "처리되지 않은 예외" | 아무도 catch 하지 않았다. 던져진 줄에서 멈춤 | 호출 스택 창, 지역 창 |
| 예외 도우미: "사용자가 처리하지 않은 예외" | 내 코드 밖(.NET 내부, 스레드 풀)으로 빠져나가기 직전 | 호출 스택, **스레드 창** |
| 멈추지 않고 결과만 틀림 | 예외가 어딘가에서 catch 되었거나, 애초에 예외가 아닌 버그 | 예외 설정 창으로 first chance 중단, 또는 2부 방식 |
| 프로세스가 통째로 사라짐 | 스택 오버플로. try/catch로 못 잡는다 | 디버거로 다시 실행 (랩 5) |

## 추적 4단계 (1부 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 예외 메시지와 그 프레임의 지역 창에서 이상한 값(null, 엉뚱한 키, 엉뚱한 형식...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다.

```
기록표 (1부용)
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

## 스택 오버플로 (랩 8)

**스택 오버플로 (랩 12, 10부의 랩 81):** 어떤 버그는 예외를 던지는 대신 프로그램을 **통째로** 사라지게 합니다. `[FAIL]`도, 예외 창도 없습니다. 거의 항상 **스택 오버플로**입니다: 스택에 너무 큰 것을 잡았거나(`stackalloc`), 함수가 자기 자신을 끝없이 부릅니다(무한 재귀). 이 예외는 `try/catch`로 잡을 수 없습니다. 디버거에서 F5 로 돌리다 멈추면, **호출 스택 창**을 보세요. 같은 함수가 수천 번 쌓여 있으면 무한 재귀입니다.

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 호출 스택 창 | 멈췄을 때 디버그 → 창 → 호출 스택 | 같은 함수가 끝없이 쌓였는지 (랩 8) |
| 중단점 적중 횟수 | 중단점 우클릭 → 적중 횟수 조건 | 재귀가 몇 번 도는지 (랩 8) |

4. 필요한 필드를 직접 쓰도록 고칩니다: `$"{Amount} 피해"`.
5. 채점기로 다른 금액(숨은 케이스)도 통과하는지 확인합니다. (참고: 랩 5의 `Gold` set 도 같은 모양의 자기 호출이었습니다. 호출 스택을 읽는 법은 두 랩이 같습니다.)

# 2부: 흐름 추적 (크래시 없음)

1부에서는 프로그램이 죽어 주었습니다. 실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **값 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 2부부터는 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되었습니다"로 보일 수 있습니다.

## 흐름 추적 4단계 (2부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `Current`는 70이어야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** F10으로 넘기며 값을 확인한다. 달라진 줄이 함수 호출이면 그 안으로(F11) 들어간다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤의 틀린 값들은 대부분 그 결과일 뿐이다.

```
기록표 (2~11부용)
틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

## 2부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 중단점 + 한 줄씩 실행 | F9, F10 | 기본 |
| 함수 안으로 / 밖으로 | F11 / Shift+F11 | 나오면 **자동 창**에 `함수명 반환` 값이 보임. 반환값을 버리는 코드(랩 15)를 잡을 때 특히 좋다 |
| 람다에 중단점 | 람다가 있는 줄에서 F9 → 줄 전체/람다 중 고르기, 또는 람다 본문에 커서를 두고 F9 | LINQ, 콜백 안을 볼 때 |
| 조건부 중단점 | 빨간 원 우클릭 → **조건** (예: `key == "fullscreen"`, `damage == 30000000`) | 반복 중 한 번만 이상할 때 |
| 추적점 | 빨간 원 우클릭 → **작업** → 메시지 `{slot} {skill}`, "실행 계속" | 멈추지 않고 **순서**와 값을 기록. 결과는 출력 창(Ctrl+Alt+O) |
| 조사식에 식 넣기 | `a.Equals(b)`, `ReferenceEquals(a, b)`, `x.GetHashCode()`, `checked(a * 100)`, `(double)f` | 조건식의 각 부분을 따로 계산, 같은 객체인지 확인 |
| 개체 ID | 지역/조사식 창에서 변수 우클릭 → **개체 ID 만들기** (`$1`) | 두 변수가 **같은 객체**인지 한눈에 볼 때 |
| 텍스트 시각화 도우미 | 문자열 값 옆의 돋보기 | 줄바꿈이 들어간 긴 문자열을 볼 때 |
| 다음 문 설정 | 노란 화살표를 끌어 옮기기 (Ctrl+Shift+F10) | 같은 코드를 다시 실행해 가설을 시험할 때 (상태는 되돌아가지 않음) |

> ⚠️ **조사식도 코드를 실행합니다.** 속성(get)이나 메서드를 조사식에 넣으면 디버거가 그 자리에서 실행합니다. 특히 `IEnumerable`을 펼쳐 **결과 보기**를 누르면 LINQ가 다시 열거됩니다. 부수 효과가 있는 코드라면 상태가 바뀝니다 (랩 10).

# 3부: 컨테이너와 컬렉션

`List`, `Dictionary`, 배열, LINQ는 매일 쓰는 만큼 버그도 많이 숨어 있습니다. 1·2부에도 컨테이너 버그가 있었습니다 (랩 2 키 비교자, 3 열거 중 수정, 9 지연 실행, 17 Equals/GetHashCode, 18 얕은 복사). 뒤의 10부에는 `ArrayPool`과 `Memory` 슬라이스(랩 79)도 나옵니다. 3부는 그 나머지 대표 함정을 모았습니다. 죽는 랩(19, 24), 결과만 틀리는 랩, 여러 스레드가 얽힌 랩(22)이 섞여 있어서, 1·2부에서 익힌 도구를 골라 써야 합니다. 랩 27은 스레드가 나오므로 8부(비동기와 동시성)를 먼저 하고 돌아와도 됩니다.

# 5부: 인터페이스와 상속

크래시는 거의 없습니다. 코드는 "분명히 그 메서드를 부르는 것처럼" 보이는데 실제로는 다른 메서드가 불립니다. 이 부의 핵심 질문은 하나입니다. **이 줄에서 실제로 어느 메서드가 불리는가?** 그것은 변수의 선언 형식(정적 형식), 객체의 실제 형식(동적 형식), 메서드가 `virtual`/`override`/`new`/명시적 구현 중 무엇인지에 따라 정해집니다.

## 콘솔에는 "메인 스레드"가 없다

WinForms·WPF의 UI 스레드나 게임 엔진의 메인 스레드에는 **SynchronizationContext**가 있습니다. 그 스레드에서 `await`하면, 기다림이 끝난 뒤 **다시 그 스레드로 돌아와서** 나머지를 실행합니다.
콘솔 앱에는 이것이 없어서, `await` 뒤의 코드는 스레드 풀의 아무 스레드에서나 이어집니다. 그래서 `.Result` 데드락 같은 유명한 버그가 콘솔에서는 **재현되지 않습니다**.

이 실습은 `Labs/Part8_Async/MainThread.cs`에 작은 게임 루프를 만들어 둡니다. 일을 큐에 받아 **스레드 하나에서만** 차례로 실행하고, 자신을 SynchronizationContext로 등록합니다. 랩 63과 67은 이 "메인 스레드" 위에서 돕니다. 이 파일에는 버그가 없습니다.

## 스택 오버플로와 버퍼 오버런 (랩 81, 82)

**스택 오버플로 (랩 81, 1부의 랩 8):** 어떤 버그는 예외를 던지는 대신 프로그램을 **통째로** 사라지게 합니다. `[FAIL]`도, 예외 창도 없습니다. 거의 항상 **스택 오버플로**입니다: 스택에 너무 큰 것을 잡았거나(`stackalloc`), 함수가 자기 자신을 끝없이 부릅니다(무한 재귀). 이 예외는 `try/catch`로 잡을 수 없습니다. 디버거에서 F5 로 돌리다 멈추면, **호출 스택 창**을 보세요. 같은 함수가 수천 번 쌓여 있으면 무한 재귀입니다.

**버퍼 오버런 (랩 82):** `unsafe` 포인터로 배열/버퍼에 쓸 때는 **경계 검사가 없습니다.** 범위를 한 칸만 넘겨도 예외가 나지 않고 **옆 메모리를 조용히 덮어씁니다.** 그래서 버그가 전혀 엉뚱한 곳(다른 변수, 다른 객체)에서 터집니다. 같은 자리를 안전한 인덱서로 쓰면 `IndexOutOfRangeException`이 나서 바로 알 수 있다는 점과 대조해 보세요.

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 조사식에 `stackalloc` 크기 | `packet.Length` | 스택에 잡는 크기가 입력에서 오는지 (랩 81) |
| 메모리 창 | 디버그 → 창 → 메모리, 포인터 주소 입력 | 포인터 쓰기가 버퍼 바로 뒤 칸을 건드리는지 (랩 82) |
| 안전 인덱서로 바꿔 보기 | `p[i]`를 잠깐 `scores[i]`로 | 범위를 넘기는지 예외로 확인 (랩 82) |

# 12부: 성능 - 틀리지는 않는데 느리다

12부의 랩은 **결과가 모두 맞습니다.** 대신 쓰레기(할당)를 많이 만들거나, 같은 일을 쓸데없이 반복하거나, 예외를 흐름 제어에 씁니다. 게임에서는 프레임이 끊기고, 서버에서는 CPU와 GC가 치솟습니다. 중단점으로는 잘 안 보이고, **측정해야** 보입니다.

판정은 실행 시간이 아니라 **측정값**으로 합니다. PC가 바쁘면 시간은 흔들리지만 할당 바이트와 연산 횟수는 흔들리지 않기 때문입니다.

| 측정값 | 재는 법 |
|---|---|
| 할당 바이트 | `GC.GetAllocatedBytesForCurrentThread()`를 앞뒤로 재서 뺀다 (`LabKit.Measure`) |
| 비교 횟수 | `IEquatable<T>.Equals` 안에서 센다 (랩 92) |
| 던져진 예외 수 | `AppDomain.CurrentDomain.FirstChanceException`에서 센다 (랩 95) |

출력에 걸린 시간(ms)도 찍히지만 참고용입니다. 각 랩은 측정 전에 한 번 미리 돌려서 JIT 컴파일 같은 첫 실행 비용을 뺍니다.

# 챌린지

1~12부를 끝낸 사람을 위한 시험입니다. 기본 부와 달리 **힌트가 없습니다.** 랩 이름은 코드(`C-1`, `B-3`)뿐이고, 증상도 한 줄만 줍니다. 무엇을 다루는지(범주), 얼마나 어려운지, 어떤 도구를 쓰는지 알려 주지 않습니다. 번호도 기본 랩(1~54)과 따로 매깁니다.

**규칙**

1. **1~12부를 먼저 끝내세요.** 챌린지는 거기서 익힌 도구와 버그 종류를 섞어 냅니다.
2. 힌트를 찾지 마세요. 챌린지 소스에는 `#region 힌트`가 없고, 해답은 [CHALLENGE_SOLUTIONS.md](CHALLENGE_SOLUTIONS.md)에 따로 있습니다. **채점기에서 `PASS`가 나온 뒤에** 맞춰 보세요.
3. 증상이 난 곳을 막지 말고 **원인**을 고치세요. 채점기의 숨은 케이스는 다른 입력과 다른 순서로 돌려서, 증상만 가린 수정을 잡아냅니다. 그때 상세에 `증상은 사라졌지만 원인이 남아 있음`이 나옵니다.
4. 판정(`Expect` 줄과 기대값을 계산하는 코드)은 고치지 마세요. 그 부분은 문제의 일부입니다.

## 분석기와 컴파일러 경고

몇몇 랩의 버그는 컴파일러나 분석기가 **미리 알려 줄 수 있었던** 것입니다. 기본으로 켜진 것과, 직접 켜야 하는 것이 있습니다.

| 번호 | 내용 | 기본 | 관련 랩 |
|---|---|---|---|
| CS8600 계열 | nullable 경고 (null일 수 있는 값을 null 아님으로) | 켜짐 (`<Nullable>enable</Nullable>`) | 1 (`!`로 눌러 둠) |
| CS0649 | 필드에 아무것도 대입하지 않음 | 켜짐 | 5 (힌트 참고) |
| CA2200 | `throw ex;`는 스택 정보를 잃는다 | 켜짐 | 7 (`NoWarn`으로 꺼 둠) |
| CS4014 | await 하지 않은 Task 호출 | 켜짐 | 28 (`_ =`로 눌러 둠) |
| CA1806 | 메서드 반환값을 버림 (`string.Replace` 등) | **꺼짐**(제안) | 14 |
| CA1305 | 문화권(`IFormatProvider`)을 지정하지 않음 | **꺼짐** | 15 |
| CA2016 | 받은 CancellationToken을 넘기지 않음 | **꺼짐**(제안) | 32 |
| CA2000 | Dispose 하지 않고 범위를 벗어남 | **꺼짐** | 33 |

꺼진 규칙을 켜려면 `BugHunt` 폴더(또는 솔루션 폴더)에 `.editorconfig`를 만들고 아래처럼 씁니다. 버그를 고친 뒤에 켜면 경고가 사라지는 것을 확인할 수 있습니다.

```ini
[*.cs]
dotnet_diagnostic.CA1806.severity = warning
dotnet_diagnostic.CA1305.severity = warning
dotnet_diagnostic.CA2016.severity = warning
dotnet_diagnostic.CA2000.severity = warning
```

> 이 프로젝트는 경고를 오류로 취급하므로, 규칙을 켜면 해당 랩을 고치기 전까지 빌드가 안 됩니다. 그게 이 규칙들의 쓸모입니다.

## 準備

必要なもの: **.NET 10 SDK**、**Visual Studio 2026** (または .NET 10 をサポートする Visual Studio、「.NET デスクトップ開発」ワークロード)

1. `BugHunt.sln` を Visual Studio で開きます。(VS 2022 17.13 以上なら `BugHunt.slnx` を開いてもかまいません。Rider、VS Code など他の IDE は `.sln` を使ってください。)
   ソリューションには採点ツールのプロジェクト `BugHunt.Grader` も入っています。F5 で実行する**スタートアッププロジェクトは `BugHunt`** です(ソリューションエクスプローラーで太字で表示されるプロジェクト)。
2. 上のツールバーで構成を **Debug** にしておきます。
3. **F5**(デバッグの開始)で実行 → メニューでラボ番号を入力。
   - 毎回同じラボを回すには: `BugHunt/Properties/launchSettings.json` の `"commandLineArgs": ""` に番号を入れます (例: `"1"`)。または、ソリューションエクスプローラーで BugHunt を右クリック → プロパティ → デバッグ → **デバッグ起動プロファイル UI を開く** → **コマンドライン引数**。
   - Ctrl+F5(デバッグなしで開始)や exe を直接実行するとデバッガーが付きません。コンソールにスタックトレースだけが残って終わります。わざとそう見るラボ(5)もありますが、基本は **F5** です。

コマンドラインから:

```bash
dotnet run --project BugHunt -- 3
```

実行出力(メニュー、判定の行)は日本語でも見られます: `dotnet run --project BugHunt -- --lang ja 3` または環境変数 `BUGHUNT_LANG=ja`。指定しなければ Windows の表示言語が日本語のとき日本語、それ以外は韓国語です。ラボのソースのコメントとヒントは一つのファイルに二つの言語が並んでいます(`#region 힌트 1 / ヒント 1`)。

### 採点ツール

直したあとは採点ツールで確かめます。リポジトリのフォルダー(この README がある所)で:

```bash
grade.bat
```

```bash
dotnet run --project BugHunt.Grader
```

二つは同じものです。別のフォルダーから `...grade.bat` を呼んでも、採点ツールは**自分が入っているリポジトリ**を採点します。一部だけ採点するにはラボ番号を付けます (`grade.bat 83-88`、`grade.bat 1,5,75-82`)。チャレンジは `grade.bat C`(深い追跡)、`grade.bat B`(ブラインド)、`grade.bat C-1,B-3` のようにコードで選びます。

採点ツール(`BugHunt.Grader` プロジェクト)がすること:

1. `BugHunt` を **Debug と Release で新しくビルド**します。ビルドが失敗すると(警告もエラーです)採点しません。
2. ラボごとに `BugHunt.exe <番号>` を**新しいプロセスで**起動します。だから一つのラボが死んでも(スタックオーバーフロー、FailFast を含む)止まっても、他のラボの採点に影響しません。
3. 画面に見える既定の入力で一回、そして**隠しケース**(ランダムなシードで作った別の入力)でさらに数回回します。期待値をコードに埋め込んで `[PASS]` だけ合わせた修正はここで引っかかります。隠しケースは3部と10〜12部のラボ、チャレンジにあります (1・2・8・9部は既定ケースのみ)。既定ケースは通ったのに隠しケースで失敗すると、詳細の前に `증상은 사라졌지만 원인이 남아 있음`(症状は消えたが原因が残っている)が付きます。
4. JIT 最適化によって結果が変わりうるラボ(39、40、42、50、チャレンジ B-8)は **Release でも**回します。すべての実行が通って初めて `PASS` です。
5. コンソールに表と総点を、リポジトリのルートに `grade-report.json` を残します。

| 結果 | 意味 |
|---|---|
| `PASS` | すべての実行が終了コード 0、`[FAIL]` なし、`[PASS]` 1個以上 |
| `FAIL` | `[FAIL]` が出たか、判定出力がない |
| `TIMEOUT` | ハング。ラボの監視タイマーが `[FAIL] 응답 없음`(応答なし)を出したか、実行一回が20秒を超えて採点ツールが強制的に終了させた |
| `CRASH` | 処理されない例外、スタックオーバーフロー、FailFast などでプロセスが死んだ。詳細に終了コードが出ます |
| `SKIP` | この環境では判定できない (ラボが `[SKIP]` を出力)。総点の分母から外れます |

最初は全部 `FAIL`、`CRASH`、`TIMEOUT` が出るのが普通です。

オプション:

| オプション | 意味 |
|---|---|
| `--config Debug` / `--config Release` | その構成一つだけで採点 |
| `--seed N` | 隠しケースのシードを固定。採点結果の一番下に出た値を入れると同じ入力で再採点します |
| `--no-hidden` | 既定ケースのみ |
| `--no-build` | ビルドを飛ばす (すでにビルドされたものを採点) |
| `--timeout MS` | 実行一回の制限時間 (既定 20000) |
| `--out パス` | レポートの場所 |
| `--lang ko` / `--lang ja` | 出力言語 (既定: 環境変数 `BUGHUNT_LANG`、なければ Windows の表示言語、それ以外は韓国語)。判定は言語に関係なく同じです |

隠しケースの一つをデバッガーで見直すには、失敗詳細の `seed` 値をコマンド引数に一緒に入れます: `"commandLineArgs": "84 --seed 123456"`。

#### grade-report.json の形式

BugHunt の四つの版(C++、C#、Unreal、Unity)が同じ形式を使います。

```json
{
  "edition": "cs",
  "version": "1",
  "total": 106,
  "passed": 12,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "PASS", "ms": 85, "detail": "" },
    { "id": 78, "title": "박자 콜백", "part": 10, "result": "CRASH", "ms": 152,
      "detail": "[Debug] 0x80131623 Process terminated. A callback was made on a garbage collected delegate ..." },
    { "id": 86, "title": "동시 거래", "part": 11, "result": "TIMEOUT", "ms": 2075,
      "detail": "응답 없음 (2000 ms 초과): 동시 거래" }
  ]
}
```

| フィールド | 形式 | 意味 |
|---|---|---|
| `edition` | 文字列 | 版の名前。このリポジトリは `"cs"` |
| `version` | 文字列 | レポート**形式**のバージョン (`"1"`) |
| `total` | 整数 | 採点したラボ数 (SKIP 含む) |
| `passed` | 整数 | `PASS` の数 |
| `labs[].id` | 整数 | ラボ番号。チャレンジは `C-n` が `100+n`、`B-n` が `200+n` (例: C-1 は 101、B-3 は 203) |
| `labs[].title` | 文字列 | ラボの名前。`--lang` で選んだ言語 |
| `labs[].part` | 整数 | 部番号 (1〜12)。チャレンジは `0` |
| `labs[].result` | 文字列 | `PASS`、`FAIL`、`TIMEOUT`、`CRASH`、`SKIP` のいずれか |
| `labs[].ms` | 整数 | かかった時間 (そのラボのすべての実行を合わせたミリ秒) |
| `labs[].detail` | 文字列 | 失敗理由の一行。`PASS` なら空文字列。隠しケースや Release で失敗したなら前に `[Release, 숨은 케이스 seed N]` のように付く。隠しケースでだけ失敗したなら、その前に `증상은 사라졌지만 원인이 남아 있음` がさらに付く。この文言も選んだ言語に従う (`--lang ja` では `[Release, 隠しケース seed N]`、`症状は消えたが原因が残っている`) |

ファイルは UTF-8(BOM なし)で、採点ツールの終了コードは満点なら 0、そうでなければ 1、ビルド失敗などで採点できなければ 2、`--lang ja` で日本語訳が抜けている出力行があれば 3 (抜けている行を最後に表示) です。キー名と `result` の値は言語に関係なく同じです。CI で使えます。

### 警告ポリシー

`BugHunt.csproj` は**警告をエラーとして扱います**(`TreatWarningsAsErrors`)。だからビルドは常に警告 0個です。
ところが現実のコードのように、このリポジトリにも誰かが警告を**切ってあったり抑え込んであったり**する所があります (`!`、`_ =`、`NoWarn`)。その場所がバグの手がかりになるラボもあります。ビルド出力がきれいでも、コードが安全とは限りません。

## 呼び出し履歴とスタックトレース

関数が関数を呼ぶと、ランタイムは「誰が自分を呼んだか」を次々と積んでおきます。その山が**呼び出し履歴(Call Stack)**です。
例外が投げられると .NET はその瞬間の呼び出し履歴を文字列にして例外の中に入れておきます。それが**スタックトレース(StackTrace)**です。

デバッガーなし(Ctrl+F5)でラボ 1 を実行すると、コンソールにこう残ります。

```
Unhandled exception. System.NullReferenceException: Object reference not set to an instance of an object.
   at BugHunt.Lab01.PrintPlayer(Player player) in F:\...\Lab01_Profile.cs:line 34    ← 一番上: 例外が出た所
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41      ← PrintPlayer を呼んだ所
   at BugHunt.Lab01.OpenFriendList() in F:\...\Lab01_Profile.cs:line 48
   at BugHunt.Lab01.Run() in F:\...\Lab01_Profile.cs:line 53
   at BugHunt.Program.Main(String[] args) in F:\...\Program.cs:line 237               ← 一番下: プログラムの始まり
```

**上から下へ読むと「誰が自分を呼んだか」**、**下から上へ読むと「プログラムがここまでどう来たか」**です。

スタックトレースの一行はこういう形です。

```
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41
      └ 名前空間.クラス.メソッド ┘└ 引数 ┘    └──── ソースファイル ────┘      └ 行 ┘
```

よく見かける変な名前たち:

| スタックに見える名前 | 意味 |
|---|---|
| `get_Gold`, `set_Gold` | `Gold` プロパティの get/set アクセサー |
| `<Run>b__0_0`, `<BindHotkeys>b__3_0` | ラムダ (かっこの中がラムダを含むメソッド) |
| `<>c__DisplayClass3_0` | ラムダがキャプチャした変数を入れるコンパイラ生成クラス |
| `<SaveAsync>d__1.MoveNext()` | async メソッドの状態機械。`MoveNext` がメソッド本体です |
| `--- End of stack trace from previous location ---` | 例外が別の所(別スレッド、await)で投げ直された境界 |
| `Repeat 12345 times:` | 同じフレームの繰り返し。スタックオーバーフローのときランタイムが畳んで見せます |

## デバッガーウィンドウの使い方

| したいこと | 方法 |
|---|---|
| 呼び出し履歴ウィンドウ | デバッグ中 **Ctrl+Alt+C** |
| ローカルウィンドウ | **Alt+4** |
| 別のフレームへ移動 | 呼び出し履歴ウィンドウで行を**ダブルクリック** → コードウィンドウがその関数の「呼び出した行」(緑の矢印)へ移り、ローカルウィンドウが**その関数の変数**に変わる |
| 例外ヘルパー | 例外で止まったときに出る吹き出し。**詳細の表示**、**内部例外の表示**、「`player` が null」のように原因の変数まで教えてくれる |
| 今の例外オブジェクトを見る | ウォッチ/イミディエイトウィンドウに **`$exception`** |
| 例外設定ウィンドウ | **Ctrl+Alt+E**。`Common Language Runtime Exceptions` の下の例外にチェックすると**最初に投げられた瞬間(first chance)**に止まる。誰が catch しても関係なく |
| 外部コードの表示 | 呼び出し履歴ウィンドウを右クリック → **外部コードの表示** |
| マイコードのみ | ツール → オプション → デバッグ → 全般 → **[マイ コードのみ] を有効にする**。オン(既定)だと .NET 内部のフレームが `[外部コード]` の一行に畳まれ、例外も「マイコードで処理されなかった」瞬間に止まる |

## デバッガーが止まる様子

| 様子 | 意味 | すること |
|---|---|---|
| 例外ヘルパー: 「ハンドルされない例外」 | 誰も catch しなかった。投げられた行で止まる | 呼び出し履歴ウィンドウ、ローカルウィンドウ |
| 例外ヘルパー: 「ユーザー未処理の例外」 | マイコードの外(.NET 内部、スレッドプール)へ抜け出る直前 | 呼び出し履歴、**スレッドウィンドウ** |
| 止まらずに結果だけ間違う | 例外がどこかで catch されたか、そもそも例外でないバグ | 例外設定ウィンドウで first chance 中断、または2部のやり方 |
| プロセスが丸ごと消える | スタックオーバーフロー。try/catch で捕まえられない | デバッガーで再実行 (ラボ 5) |

## 追跡の4ステップ (1部共通)

1. **どこで止まったか?** 呼び出し履歴で**マイコードが出る最初の行**を探す。
2. **何がおかしいか?** 例外メッセージとそのフレームのローカルウィンドウで、おかしな値(null、見当違いのキー、見当違いの型…)を探す。
3. **その値はどこから来たか?** 一つ**下**のフレーム(= 自分を呼んだ関数)をダブルクリックして、その値を渡した所を見る。出どころが出るまで繰り返す。
4. **本当の原因は?** 止まった所ではなく**おかしな値が最初に作られた所**を直す。

> 💡 核心: **死んだ所 ≠ 間違えた所**であることがほとんどです。

```
記録表 (1部用)
止まった関数:            
おかしな値:              
その値が来たフレーム:     
本当の原因:              
修正:                    
```

## スタックオーバーフロー (ラボ 8)

**スタックオーバーフロー (ラボ 12、10部のラボ 81):** あるバグは例外を投げる代わりにプログラムを**丸ごと**消します。`[FAIL]` も例外ウィンドウもありません。ほとんどの場合**スタックオーバーフロー**です: スタックに大きすぎるものを取ったか(`stackalloc`)、関数が自分自身を延々と呼んでいます(無限再帰)。この例外は `try/catch` で捕まえられません。デバッガーで F5 で動かして止まったら、**呼び出し履歴ウィンドウ**を見てください。同じ関数が何千回も積まれていれば無限再帰です。

| ツール | 使い方 | いつ |
|---|---|---|
| 呼び出し履歴ウィンドウ | 止まったときデバッグ → ウィンドウ → 呼び出し履歴 | 同じ関数が延々と積まれているか (ラボ 8) |
| ブレークポイントのヒットカウント | ブレークポイントを右クリック → ヒットカウント条件 | 再帰が何回回るか (ラボ 8) |

# 2部: フロー追跡 (クラッシュなし)

1部ではプログラムが死んでくれました。実務のバグのほとんどはそうではありません。プログラムは最後まできちんと回り、**値が一つ間違うだけ**です。このときは**自分で止めて、自分で追わなければ**なりません。

> 2部からは **Debug** 構成でやってください。Release は最適化のせいで行が飛ばされたり、変数が「最適化されました」と表示されたりすることがあります。

## フロー追跡の4ステップ (2部共通)

1. **期待を先に書く。** 「この行が終われば `Current` は 70 のはず」のように、追う前に各ステップの期待値を決める。
2. **間違った結果に一番近い所から止める。** [FAIL] が出た値を作る関数の入口にブレークポイントを置く。
3. **期待と最初に食い違う行を探す。** F10 で越えながら値を確かめる。食い違った行が関数呼び出しなら、その中へ(F11)入る。
4. **「最初に食い違った所」を直す。** そのあとの間違った値は、ほとんどがその結果にすぎない。

```
記録表 (2〜11部用)
間違った結果:            
止めた位置:              
期待値 → 実際の値:        
最初にずれた行:          
本当の原因:              
修正:                    
```

## 2部で使うツール

| ツール | 使い方 | いつ |
|---|---|---|
| ブレークポイント + 一行ずつ実行 | F9、F10 | 基本 |
| 関数の中へ / 外へ | F11 / Shift+F11 | 出ると**自動変数ウィンドウ**に `関数名 戻り値` が見える。戻り値を捨てるコード(ラボ 15)を捕まえるときに特によい |
| ラムダにブレークポイント | ラムダのある行で F9 → 行全体/ラムダから選ぶ、またはラムダ本体にカーソルを置いて F9 | LINQ、コールバックの中を見るとき |

# 4部: C# 言語の罠

この部のバグは**声に出して読むと正しく見えます。** 演算子の優先順位、値型のコピー、ラムダの変数キャプチャ、文字列のインターン、浮動小数点、既定の丸め規則のように、「言語がそう定義した」動作が読む人の期待と違うだけです。そのためこの部では、**式を分解してウォッチに一つずつ入れてみること**が一番強い道具です。一行全体ではなく、その行の部分式がそれぞれどんな値と型を持つか確かめてください。

## 4部で使うツール

| ツール | 使い方 | いつ |
|---|---|---|
| ウォッチに部分式を入れる | 行の一部を選択 → 右クリック → **ウォッチに追加**、括弧を変えながら比べる | 優先順位がどう結び付いたか (ラボ 32)、丸め規則の比較 (ラボ 37) |

# 8部: 非同期と並行性

非同期のバグは**呼び出し履歴が嘘をついているように**見えます。`await` のあとのコードは、元々呼んだ関数の上ではなく、あとで別のスレッド(または同じスレッドの次の順番)で続けて実行されるからです。
だから8部では「今、誰が何を待っているか」を見せてくれるウィンドウを使います。

## 8部で使うツール

| ツール | 使い方 | いつ |
|---|---|---|
| すべて中断 | デバッグ → **すべて中断** (Ctrl+Alt+Break) | プログラムが止まったとき(デッドロック)、止まった瞬間のすべてのスレッドを見るため |
| スレッドウィンドウ | **Ctrl+Alt+H** | 今どのスレッドで止まったか、スレッド名(`Main Thread (게임 루프)`、`.NET TP Worker`) |
| 並列スタックウィンドウ | デバッグ → ウィンドウ → **並列スタック** (Ctrl+Shift+D, S) | すべてのスレッドの呼び出し履歴を一枚の図で。上の方で**スレッド / タスク**の表示切り替え |
| タスクウィンドウ | デバッグ → ウィンドウ → **タスク** (Ctrl+Shift+D, K) | まだ終わっていない `Task` たちと状態(アクティブ、待機中、スケジュール済み)、何を待っているか |
| ブレークポイントのフィルター | 赤い丸を右クリック → 条件 → **フィルター** → `ThreadId = 12` | 複数のスレッドが同じコードを回るとき、一つのスレッドだけで止める |
| スレッドの固定 | スレッドウィンドウの旗アイコン | 関心のあるスレッドだけ表示 |
| 最初の例外(first chance)で中断 | 例外設定(**Ctrl+Alt+E**) → Common Language Runtime Exceptions で型にチェック | 例外が**投げられる瞬間**に止まる。どこかで捕まって消えたり(ラボ 69)、あとで別の所で投げ直される(ラボ 71)例外の出発点 |
| 例外フィルター | `catch (OperationCanceledException) when (条件)` | 条件が偽ならその catch はないかのように通り過ぎる。スタックを巻き戻す前に評価されるので、デバッガーが元の位置で止まったまま見られる (ラボ 70) |

## コンソールには「メインスレッド」がない

WinForms・WPF の UI スレッドやゲームエンジンのメインスレッドには **SynchronizationContext** があります。そのスレッドで `await` すると、待ちが終わったあと**再びそのスレッドに戻ってきて**残りを実行します。
コンソールアプリにはこれがないので、`await` のあとのコードはスレッドプールの任意のスレッドで続きます。だから `.Result` デッドロックのような有名なバグがコンソールでは**再現されません**。

この実習は `Labs/Part8_Async/MainThread.cs` に小さなゲームループを作ってあります。仕事をキューで受けて**スレッド一つだけで**順に実行し、自分を SynchronizationContext として登録します。ラボ 63 と 67 はこの「メインスレッド」の上で回ります。このファイルにバグはありません。

## スタックオーバーフローとバッファオーバーラン (ラボ 81、82)

**スタックオーバーフロー (ラボ 81、1部のラボ 8):** あるバグは例外を投げる代わりにプログラムを**丸ごと**消します。`[FAIL]` も例外ウィンドウもありません。ほとんどの場合**スタックオーバーフロー**です: スタックに大きすぎるものを取ったか(`stackalloc`)、関数が自分自身を延々と呼んでいます(無限再帰)。この例外は `try/catch` で捕まえられません。デバッガーで F5 で動かして止まったら、**呼び出し履歴ウィンドウ**を見てください。同じ関数が何千回も積まれていれば無限再帰です。

**バッファオーバーラン (ラボ 82):** `unsafe` ポインターで配列・バッファに書くときは**範囲検査がありません。** 範囲を一マス越えただけでも例外が出ず、**隣のメモリを黙って上書きします。** だからバグがまったく見当違いの所(別の変数、別のオブジェクト)で弾けます。同じ場所を安全なインデクサーで書けば `IndexOutOfRangeException` が出てすぐ分かる、という点と対比してください。

|---|---|---|
| ウォッチに `stackalloc` のサイズ | `packet.Length` | スタックに取るサイズが入力から来るか (ラボ 81) |
| メモリウィンドウ | デバッグ → ウィンドウ → メモリ、ポインターのアドレスを入力 | ポインターの書き込みがバッファのすぐ後ろのマスを触るか (ラボ 82) |
| 安全なインデクサーに置き換えてみる | `p[i]` を一時的に `scores[i]` に | 範囲を越えているか例外で確認 (ラボ 82) |

# 11部: ハング - 無限ループとデッドロック

クラッシュも例外もなく**ただ止まる**バグです。コンソールには何も出ず、デバッガーも自分では止まりません。このときすることは一つです。**止まった瞬間のすべてのスレッドを見る。**

> 11部のラボは本当に永遠に止まるわけではありません。各ラボは `LabKit.FinishesWithin`(監視タイマー)の下で回り、**2秒**が過ぎると `[FAIL] 응답 없음 (2000 ms 초과)`(応答なし。2000 ms 超過)を出力して終わります。
> - デバッガーで(F5)実行すると失敗で終わらせず待ち続けます。メッセージが出たらそのとき**すべて中断**を押してください。
> - デバッガーなしで実行すると `계속하려면 Enter`(続けるには Enter)で待ちます。その間、止まったスレッドはそのまま残っているので、`dotnet-stack` や `dotnet-dump` で覗いたり、VS で**デバッグ → プロセスにアタッチ**したりできます。

# 12部: パフォーマンス - 間違ってはいないが遅い

12部のラボは**結果がすべて合っています。** その代わりゴミ(割り当て)をたくさん作ったり、同じことを無駄に繰り返したり、例外をフロー制御に使ったりします。ゲームではフレームが詰まり、サーバーでは CPU と GC が跳ね上がります。ブレークポイントではなかなか見えず、**測定して**見えます。

判定は実行時間ではなく**測定値**で行います。PC が忙しいと時間はぶれますが、割り当てバイトと演算回数はぶれないからです。

| 測定値 | 測り方 |
|---|---|
| 割り当てバイト | `GC.GetAllocatedBytesForCurrentThread()` を前後で測って引く (`LabKit.Measure`) |
| 比較回数 | `IEquatable<T>.Equals` の中で数える (ラボ 92) |
| 投げられた例外の数 | `AppDomain.CurrentDomain.FirstChanceException` で数える (ラボ 95) |

出力にかかった時間(ms)も出ますが参考用です。各ラボは測定の前に一度ウォームアップで回して、JIT コンパイルのような初回実行のコストを除きます。

## アナライザーとコンパイラ警告

いくつかのラボのバグは、コンパイラやアナライザーが**あらかじめ知らせてくれたはずの**ものです。既定で有効なものと、自分で有効にしなければならないものがあります。

| 番号 | 内容 | 既定 | 関連ラボ |
|---|---|---|---|
| CS8600 系 | nullable 警告 (null でありうる値を null でないとして) | 有効 (`<Nullable>enable</Nullable>`) | 1 (`!` で抑え込み) |
| CS0649 | フィールドに何も代入していない | 有効 | 5 (ヒント参照) |
| CA2200 | `throw ex;` はスタック情報を失う | 有効 | 7 (`NoWarn` で切ってある) |
| CS4014 | await していない Task 呼び出し | 有効 | 28 (`_ =` で抑え込み) |
| CA1806 | メソッドの戻り値を捨てる (`string.Replace` など) | **無効**(提案) | 14 |
| CA1305 | カルチャ(`IFormatProvider`)を指定していない | **無効** | 15 |
| CA2016 | 受け取った CancellationToken を渡していない | **無効**(提案) | 32 |
| CA2000 | Dispose せずにスコープを抜ける | **無効** | 33 |

無効な規則を有効にするには、`BugHunt` フォルダー(またはソリューションフォルダー)に `.editorconfig` を作って下のように書きます。バグを直したあとに有効にすると、警告が消えるのを確認できます。

```ini
[*.cs]
dotnet_diagnostic.CA1806.severity = warning
dotnet_diagnostic.CA1305.severity = warning
dotnet_diagnostic.CA2016.severity = warning
dotnet_diagnostic.CA2000.severity = warning
```

> このプロジェクトは警告をエラーとして扱うので、規則を有効にするとそのラボを直すまでビルドが通りません。それがこれらの規則の使いどころです。
