# N부: 인터페이스와 상속

크래시는 거의 없습니다. 코드는 "분명히 그 메서드를 부르는 것처럼" 보이는데 실제로는 다른 메서드가 불립니다. 이 부의 핵심 질문은 하나입니다. **이 줄에서 실제로 어느 메서드가 불리는가?** 그것은 변수의 선언 형식(정적 형식), 객체의 실제 형식(동적 형식), 메서드가 `virtual`/`override`/`new`/명시적 구현 중 무엇인지에 따라 정해집니다.

## N부에서 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| **F11로 들어가기** | 호출하는 줄에서 F11 | "불릴 줄 알았던 메서드"가 아니라 **실제로 불리는 메서드**로 들어갑니다. 이 부에서 가장 빠른 확인법 (랩 90·91) |
| 모든 후보에 중단점 | 같은 이름의 메서드(기반, 파생, 인터페이스 기본 구현, 명시적 구현)에 모두 F9 | 어느 쪽에서 멈추는지로 호출 경로를 확인 (랩 90·91·92·95) |
| 조사식의 `GetType()` | `s.GetType()`, `bag.GetType()` | 선언 형식과 실제 형식 비교 (랩 90·97) |
| 조사식의 캐스팅 | `((Quest)r).Gold` vs `r.Gold` | 같은 객체를 다른 형식으로 보면 값이 달라지는지 (랩 92) |
| 호출 스택 창 | Ctrl+Alt+C | 생성자 안에서 불린 가상 메서드: 누가 불렀고 파생 생성자 본문은 실행됐는지 (랩 94) |
| 개체 ID | 변수 우클릭 → 개체 ID 만들기 | struct 에는 만들 수 없음. 박싱 사본을 고치고 있다는 단서 (랩 93) |
| 조사식의 `Comparer` | `favorites.Comparer` | 컬렉션이 어느 `Equals`를 부르는지 (랩 95) |

## 따라 해 보기: 랩 94 (유닛 소환)

1. 명령 인수에 번호를 넣고 **F5**. `[FAIL] 기사 로한 소환 직후 현재 체력 = 최대 체력 (기대: 170, 실제: 100)`.
2. `Knight.MaxHp`에 **F9**, 다시 F5. 처음 멈췄을 때 **지역 창**에서 `armor`와 `baseHp`를 봅니다. `baseHp`는 100인데 `armor`는 **0**입니다.
3. **호출 스택 창**(Ctrl+Alt+C)을 엽니다. `MaxHp`를 부른 것은 `Knight` 생성자가 아니라 **`Unit` 생성자**입니다. 그 줄을 더블클릭하면 `Hp = MaxHp();`로 갑니다.
4. 한 줄 더 내려가서 `Knight` 생성자의 `this.armor = armor;`에도 F9를 걸고 처음부터 다시 실행합니다. 두 중단점 중 어느 쪽이 먼저 멈추나요? → *처음 어긋난 줄*
5. `baseHp = 100`은 왜 이미 들어 있었을까요? 필드 이니셜라이저와 생성자 본문은 실행되는 시점이 다릅니다.
6. 생성자에서 가상 메서드를 부르지 않게 고친 뒤, 채점기로 마법사(숨은 케이스)도 통과하는지 확인합니다.

# N부: 인터페이스와 상속

## Lab 90 — `new`로 숨긴 메서드는 기반 형식으로 부르면 안 불린다
```
FireSkill.Damage 중단점:   TotalDamage 에서는 안 멈춤 (Run 의 기대값 계산에서만 멈춤)
F11 (s.Damage(attack)):    Skill.Damage 로 들어감
조사식 s.GetType():        FireSkill   (정적 형식은 Skill)
진짜 원인:  FireSkill·IceSkill 의 Damage 가 override 가 아니라 new. 기반 메서드를 덮어쓰지 않고 같은 이름의 새 메서드를 만들었다.
           Skill 형식의 변수로 부르면 Skill.Damage 가 불린다. new 를 지우면 CS0108 경고가 나서 누군가 new 로 눌러 둔 것.
```
**수정:** 두 파생 클래스 모두 `public override int Damage(int attack)`.
**교훈:** CS0108("숨깁니다. 의도한 것이면 new 를 쓰세요")은 대개 `override`를 빠뜨렸다는 뜻입니다. `new`는 기반 클래스를 바꿀 수 없는데 같은 이름이 꼭 필요한 드문 경우에만 씁니다. 불 스킬만 고치면 숨은 케이스(얼음 스킬)에서 걸립니다.

## Lab 91 — 시그니처가 다른 메서드 대신 인터페이스 기본 구현이 불림
```
Boss.DropCount 중단점:     RollDrops 에서는 안 멈춤
F11 (monster.DropCount):   IDropSource.DropCount 의 기본 구현 (=> 1) 으로 들어감
진짜 원인:  Boss.DropCount(int, bool = false), Elite.DropCount(long) 은 인터페이스의 int DropCount(int) 와 시그니처가 달라서
           구현으로 인정되지 않는다. 인터페이스에 기본 구현이 있으니 컴파일 오류도 경고도 없다.
```
**수정:** 시그니처를 인터페이스와 똑같이 맞춘다.
```csharp
public int DropCount(int luck) => baseDrops + luck / 10;      // Boss
public int DropCount(int luck) => 2 + luck / 20;              // Elite
```
정예 보스 같은 변형은 생성자 인자나 별도 오버로드로 받는다.
**교훈:** 선택적 매개변수를 붙이거나 매개변수 형식을 넓히면(`int` → `long`) 호출하는 쪽 코드는 똑같아 보여도 **다른 메서드**입니다. 기본 구현(DIM)이 있는 인터페이스는 "구현을 빠뜨려도 컴파일된다"는 위험을 같이 들고 옵니다. 기본 구현을 잠깐 지워 보면 구현이 빠진 클래스가 컴파일 오류로 드러납니다.

## Lab 92 — 명시적 인터페이스 구현이 다른 값을 돌려줌
```
조사식 r.Gold:            600     (IReward 로 봄 → 명시적 구현)
조사식 ((Quest)r).Gold:   1200    (Quest 로 봄 → public 구현)
진짜 원인:  Quest 에 Gold 가 둘. public int Gold(배율 적용)와 int IReward.Gold(배율 없음).
           퀘스트 창은 Quest 로, 정산은 IReward 로 읽어서 서로 다른 구현이 불린다.
```
**수정:** `int IReward.Gold => Gold;` 또는 명시적 구현을 지운다(public `Gold`가 인터페이스를 구현).
**교훈:** 명시적 구현은 이름 충돌을 피하거나 멤버를 인터페이스 쪽으로만 보이게 할 때 씁니다. 두 번째 로직을 두는 자리가 아닙니다. 정산에서 2배를 하는 수정은 숨은 케이스(다른 배율)에서 걸립니다.

## Lab 93 — struct를 인터페이스로 다뤄서 박싱 사본만 바뀜
```
Buff.Tick 중단점:     불림. this.Turns 가 줄어드는 것도 보임
EndTurn 뒤 buffs[0].Turns:   그대로
Tick 안에서 this 에 개체 ID 만들기:   불가 (값 형식)
진짜 원인:  foreach (ITickable buff in buffs) 가 칸마다 Buff 를 박싱해 힙 사본을 만들고, Tick 은 그 사본을 고친다.
```
**수정 (택1):**
- `for (int i = 0; i < buffs.Length; i++) buffs[i].Tick();`
- `foreach (ref Buff buff in buffs.AsSpan()) buff.Tick();`
- 제네릭 제약: `static void TickAll<T>(Span<T> items) where T : ITickable { foreach (ref T it in items) it.Tick(); }`
- 바뀌는 데이터면 `class`로.

**교훈:** 값 형식을 인터페이스, `object`로 바꾸는 순간 복사본이 생깁니다(랩 4 박싱 해제, 랩 11 박싱된 `==`, 랩 20 `List<struct>` 인덱서와 같은 뿌리). 바뀌는 struct에 인터페이스를 붙이면 이 버그가 숨어 들어오기 쉽습니다.

## Lab 94 — 생성자 안의 가상 호출
```
Knight.MaxHp 중단점 (처음 멈춤):   armor == 0, baseHp == 100
호출 스택:   Unit..ctor → Knight.MaxHp   (Knight..ctor 본문은 아직)
진짜 원인:  생성 순서는 파생 필드 이니셜라이저 → 기반 생성자 → 파생 생성자 본문.
           기반 생성자가 부른 가상 메서드는 이미 Knight.MaxHp 로 가지만, armor 는 파생 생성자 본문에서야 들어간다.
```
**수정:** 기반 생성자가 필요한 값을 인자로 받는다.
```csharp
protected Unit(string name, int maxHp) { Name = name; Hp = maxHp; }
public Knight(string name, int armor) : base(name, 100 + armor * 10) { this.armor = armor; }
public Mage(string name, int wisdom) : base(name, 60 + wisdom * 5) { this.wisdom = wisdom; }
```
또는 체력 채우기를 생성이 끝난 뒤의 `Spawn()` 단계로 옮긴다.
**교훈:** 생성자에서 가상 메서드를 부르면 파생 클래스가 아직 준비되지 않은 객체를 보게 됩니다(CA2214). 필드 이니셜라이저(`baseHp = 100`)는 기반 생성자보다 **먼저**, 생성자 본문은 **나중에** 실행된다는 차이가 증상을 헷갈리게 만듭니다. `Knight` 생성자 끝에서 `Hp`를 다시 채우는 수정은 숨은 케이스(마법사)에서 걸립니다.

## Lab 95 — `Equals(object)`와 `IEquatable<T>.Equals`가 다른 규칙
```
bag.Contains(loot):         true    → Equals(ItemStack) (Id 만 비교)
favorites.Contains(loot):   false   → Equals(object)    (Id + 품질 비교)
조사식 favorites.Comparer:  ObjectEqualityComparer<IItem>
진짜 원인:  EqualityComparer<T>.Default 는 T 가 IEquatable<T> 이면 Equals(T), 아니면 Equals(object) 를 부른다.
           List<ItemStack> 은 T = ItemStack, HashSet<IItem> 은 T = IItem 이라 서로 다른 Equals 를 탄다.
```
**수정:** `public override bool Equals(object? obj) => Equals(obj as ItemStack);` (한 규칙에 위임)
**교훈:** 같은 형식이 `IEquatable<T>`, `object`, 인터페이스 형식의 컬렉션, `==` 연산자 등 여러 경로로 비교됩니다. 모든 경로가 같은 규칙이어야 하고, `GetHashCode`도 같은 규칙이어야 합니다(랩 17은 해시가 어긋난 경우). 즐겨찾기를 `HashSet<ItemStack>`으로 바꾸는 수정도 통과하지만, 다른 `IItem` 구현이 들어오는 순간 다시 깨집니다.

## Lab 96 — 기반 형식을 먼저 검사해서 파생 분기에 닿지 않음
```
return 500; 중단점:   안 멈춤
조사식 killed is Enemy:       true   (보스도 Enemy)
조사식 killed is BossEnemy:   true
진짜 원인:  if (killed is Enemy) 가 첫 분기라서 보스·정예도 모두 10G. 뒤의 else if 두 개는 닿을 수 없다.
           같은 순서를 switch 식으로 쓰면 CS8120("이미 앞의 case 가 처리")으로 컴파일이 안 되지만, if/else if 에는 그런 검사가 없다.
```
**수정:** 가장 파생된 형식부터 검사한다 (보스 → 정예 → 일반 적). 더 나은 방법은 `switch` 식으로 써서 컴파일러가 순서를 검사하게 하거나, `Unit`에 `virtual int KillReward`를 둬서 형식 검사 자체를 없애는 것.
**교훈:** 보스 분기만 위로 올리면 숨은 케이스(정예가 섞인 웨이브)에서 걸립니다.

## Lab 97 — 배열 공변성
```
예외:      ArrayTypeMismatchException: Attempted to access an element as a type incompatible with the array.
멈춘 곳:   Put 의 bag[slot] = item
조사식 bag.GetType():   Lab97+Weapon[]   (선언 형식은 Item[])
진짜 원인:  CreateBag 이 new Weapon[size] 를 만들어 Item[] 로 돌려줬다. 배열 공변성 덕에 컴파일은 되지만 실제 배열은 Weapon 만 받는다.
```
**수정:** `var bag = new Item[size];`
**교훈:** 참조 형식 배열은 공변이라 `Weapon[]`을 `Item[]` 변수에 넣을 수 있지만, 쓰기는 런타임 검사로 막힙니다. `List<T>`는 공변이 아니어서 이 실수가 컴파일되지 않고, 읽기 전용 공변성은 `IEnumerable<out T>`, `IReadOnlyList<out T>`로 얻습니다. 예외를 삼키고 건너뛰면 물약이 사라져 채워진 칸 수에서 걸립니다. (블라인드 챌린지 B-4도 같은 범주입니다)

| | struct를 인터페이스로 다뤄 박싱 사본만 바뀜 | 93 |
| | 생성자 안의 가상 호출 | 94 |
| | `Equals(object)`와 `IEquatable<T>.Equals` 불일치 | 95 |
| | 형식 검사 순서 (`if`/`else if`에서 기반 형식 먼저) | 96 |
| | 배열 공변성 (`ArrayTypeMismatchException`) | 97 (블라인드 B-4도) |
| | 기반 클래스 `Equals`를 파생에서 확장해 대칭성이 깨짐 (`a.Equals(b) != b.Equals(a)`), `abstract` 대신 빈 `virtual`로 재정의 누락, 제네릭 인터페이스 공변·반공변(`in`/`out`) 변환 실패, `sealed` 아닌 클래스의 `record` 상속과 `EqualityContract` | 미포함 |

기존 **컨테이너** 범주의 미포함 줄에서 "배열 공변성(`ArrayTypeMismatchException`)"을 지우고 `Dictionary 열거 순서에 기대기, IReadOnlyList를 캐스팅해서 수정 | 미포함`으로 바꿉니다.

미포함 사유: 대칭성 깨짐은 랩 95와 같은 판정(컬렉션마다 다른 답)으로 겹치고, 재정의 누락과 공변·반공변은 주로 컴파일 오류로 드러나 디버거 추적 대상이 아닙니다.

## 일본어판: 부 소개와 도구

# N部: インターフェイスと継承

クラッシュはほとんどありません。コードは「確かにそのメソッドを呼んでいるように」見えますが、実際には別のメソッドが呼ばれます。この部の核心の問いは一つです。**この行で実際にどのメソッドが呼ばれるのか?** それは変数の宣言の型(静的な型)、オブジェクトの実際の型(動的な型)、メソッドが `virtual`/`override`/`new`/明示的な実装のどれかによって決まります。

| ツール | 使い方 | いつ |
|---|---|---|
| **F11 でステップイン** | 呼び出す行で F11 | 「呼ばれるはずのメソッド」ではなく**実際に呼ばれるメソッド**に入ります。この部で一番速い確認方法です |
| すべての候補にブレークポイント | 同じ名前のメソッド(基底、派生、インターフェイスの既定の実装、明示的な実装)すべてに F9 | どちらで止まるかで呼び出し経路を確認します |
| ウォッチの `GetType()` | `s.GetType()`、`bag.GetType()` | 宣言の型と実際の型を比べます |
| ウォッチでのキャスト | `((Quest)r).Gold` と `r.Gold` | 同じオブジェクトを別の型で見ると値が変わるか |
| 呼び出し履歴ウィンドウ | Ctrl+Alt+C | コンストラクター内で呼ばれた仮想メソッド: 誰が呼び、派生コンストラクター本体は実行済みか |
| オブジェクト ID | 変数を右クリック → オブジェクト ID の作成 | struct には作れません。ボックス化コピーを直している手がかりです |
| ウォッチの `Comparer` | `favorites.Comparer` | コレクションがどの `Equals` を呼ぶか |

## 일본어판: 기록표 (SOLUTIONS)

### Lab 90 — `new` で隠したメソッドは基底の型で呼ぶと呼ばれない
```
FireSkill.Damage のブレークポイント:  TotalDamage では止まらない (Run の期待値計算でだけ止まる)
F11 (s.Damage(attack)):              Skill.Damage に入る
ウォッチ s.GetType():                 FireSkill   (静的な型は Skill)
本当の原因:  FireSkill・IceSkill の Damage が override ではなく new。基底メソッドを上書きせず、同じ名前の新しいメソッドを作った。
            Skill 型の変数で呼ぶと Skill.Damage が呼ばれる。new を消すと CS0108 警告が出るので、誰かが new で黙らせた。
```
**修正:** 二つの派生クラスとも `public override int Damage(int attack)`。
**教訓:** CS0108(「隠蔽します。意図的なら new を使ってください」)はたいてい `override` の書き忘れです。`new` は基底クラスを変えられないのに同じ名前がどうしても必要な、まれな場合だけに使います。炎スキルだけ直すと隠しケース(氷スキル)で引っかかります。

### Lab 91 — シグネチャが違うメソッドの代わりにインターフェイスの既定の実装が呼ばれる
```
Boss.DropCount のブレークポイント:   RollDrops では止まらない
F11 (monster.DropCount):           IDropSource.DropCount の既定の実装 (=> 1) に入る
本当の原因:  Boss.DropCount(int, bool = false)、Elite.DropCount(long) はインターフェイスの int DropCount(int) とシグネチャが違うので
            実装と認められない。インターフェイスに既定の実装があるのでコンパイルエラーも警告も出ない。
```
**修正:** シグネチャをインターフェイスと同じにします(`public int DropCount(int luck)`)。精鋭ボスのような変種はコンストラクター引数か別のオーバーロードで受け取ります。
**教訓:** 省略可能な引数を付けたり引数の型を広げたり(`int` → `long`)すると、呼び出し側のコードは同じに見えても**別のメソッド**です。既定の実装(DIM)があるインターフェイスは「実装を忘れてもコンパイルが通る」という危険を一緒に持ち込みます。

### Lab 92 — 明示的なインターフェイス実装が違う値を返す
```
ウォッチ r.Gold:            600     (IReward として見る → 明示的な実装)
ウォッチ ((Quest)r).Gold:   1200    (Quest として見る → public 実装)
本当の原因:  Quest に Gold が二つ。public int Gold(倍率適用)と int IReward.Gold(倍率なし)。
            クエスト画面は Quest として、精算は IReward として読むので違う実装が呼ばれる。
```
**修正:** `int IReward.Gold => Gold;`、または明示的な実装を消します。
**教訓:** 明示的な実装は名前の衝突を避けたり、メンバーをインターフェイス側からだけ見せたりするときに使います。二つ目のロジックを置く場所ではありません。

### Lab 93 — struct をインターフェイスとして扱い、ボックス化コピーだけが変わる
```
Buff.Tick のブレークポイント:  呼ばれる。this.Turns が減るのも見える
EndTurn のあとの buffs[0].Turns:  そのまま
Tick の中で this にオブジェクト ID を作成:  不可 (値型)
本当の原因:  foreach (ITickable buff in buffs) が要素ごとに Buff をボックス化してヒープのコピーを作り、Tick はそのコピーを直す。
```
**修正(いずれか):** `for` とインデクサー、`foreach (ref Buff buff in buffs.AsSpan())`、ジェネリック制約 `where T : ITickable`、または `class` にする。
**教訓:** 値型をインターフェイスや `object` に変えた瞬間にコピーができます(ラボ4、11、20と同じ根)。

### Lab 94 — コンストラクター内の仮想呼び出し
```
Knight.MaxHp のブレークポイント (最初の停止):  armor == 0, baseHp == 100
呼び出し履歴:  Unit..ctor → Knight.MaxHp   (Knight..ctor 本体はまだ)
本当の原因:  生成の順番は 派生フィールド初期化子 → 基底コンストラクター → 派生コンストラクター本体。
```
**修正:** 基底コンストラクターが必要な値を引数で受け取ります(`protected Unit(string name, int maxHp)`、`: base(name, 100 + armor * 10)`)。または HP を満たす処理を生成後の `Spawn()` に移します。
**教訓:** コンストラクターで仮想メソッドを呼ぶと、派生クラスがまだ準備できていないオブジェクトを見ることになります(CA2214)。`Knight` のコンストラクターの最後で `Hp` を入れ直す修正は隠しケース(魔法使い)で引っかかります。

### Lab 95 — `Equals(object)` と `IEquatable<T>.Equals` が違う規則
```
bag.Contains(loot):         true    → Equals(ItemStack) (Id だけ比較)
favorites.Contains(loot):   false   → Equals(object)    (Id + 品質を比較)
ウォッチ favorites.Comparer:  ObjectEqualityComparer<IItem>
本当の原因:  EqualityComparer<T>.Default は T が IEquatable<T> なら Equals(T)、そうでなければ Equals(object) を呼ぶ。
```
**修正:** `public override bool Equals(object? obj) => Equals(obj as ItemStack);`
**教訓:** 同じ型がいくつもの経路で比較されます。すべての経路が同じ規則でなければならず、`GetHashCode` も同じ規則でなければなりません(ラボ17)。

### Lab 96 — 基底型を先に調べたので派生の分岐に届かない
```
return 500; のブレークポイント:  止まらない
ウォッチ killed is Enemy:       true   (ボスも Enemy)
本当の原因:  if (killed is Enemy) が最初の分岐なのでボス・精鋭もすべて 10G。switch 式なら CS8120 でコンパイルできない。
```
**修正:** 最も派生した型から調べます(ボス → 精鋭 → 通常の敵)。`switch` 式にするか、`virtual int KillReward` で型チェック自体をなくすとなお良いです。
**教訓:** ボスの分岐だけ上に上げると、隠しケース(精鋭が混ざったウェーブ)で引っかかります。

### Lab 97 — 配列の共変性
```
例外:      ArrayTypeMismatchException
止まった所: Put の bag[slot] = item
ウォッチ bag.GetType():  Lab97+Weapon[]   (宣言の型は Item[])
本当の原因:  CreateBag が new Weapon[size] を作って Item[] として返した。
```
**修正:** `var bag = new Item[size];`
**教訓:** 参照型の配列は共変なので `Weapon[]` を `Item[]` の変数に入れられますが、書き込みは実行時チェックで弾かれます。`List<T>` は共変ではないのでこの間違いはコンパイルが通りません。
