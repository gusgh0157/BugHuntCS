## README에 들어갈 부분 (한국어)

(각 랩을 해당 부의 끝 근처에 끼워 넣습니다. 아래는 랩 소개 문단입니다.)

**스택 오버플로 (랩 121, 122):** 어떤 버그는 예외를 던지는 대신 프로그램을 **통째로** 사라지게 합니다. `[FAIL]`도, 예외 창도 없습니다. 거의 항상 **스택 오버플로**입니다: 스택에 너무 큰 것을 잡았거나(`stackalloc`), 함수가 자기 자신을 끝없이 부릅니다(무한 재귀). 이 예외는 `try/catch`로 잡을 수 없습니다. 디버거에서 F5 로 돌리다 멈추면, **호출 스택 창**을 보세요. 같은 함수가 수천 번 쌓여 있으면 무한 재귀입니다.

**버퍼 오버런 (랩 123):** `unsafe` 포인터로 배열/버퍼에 쓸 때는 **경계 검사가 없습니다.** 범위를 한 칸만 넘겨도 예외가 나지 않고 **옆 메모리를 조용히 덮어씁니다.** 그래서 버그가 전혀 엉뚱한 곳(다른 변수, 다른 객체)에서 터집니다. 같은 자리를 안전한 인덱서로 쓰면 `IndexOutOfRangeException`이 나서 바로 알 수 있다는 점과 대조해 보세요.

## 쓰는 도구

| 도구 | 하는 법 | 언제 |
|---|---|---|
| 호출 스택 창 | 멈췄을 때 디버그 → 창 → 호출 스택 | 같은 함수가 끝없이 쌓였는지 (랩 122) |
| 중단점 적중 횟수 | 중단점 우클릭 → 적중 횟수 조건 | 재귀가 몇 번 도는지 (랩 122) |
| 조사식에 `stackalloc` 크기 | `packet.Length` | 스택에 잡는 크기가 입력에서 오는지 (랩 121) |
| 메모리 창 | 디버그 → 창 → 메모리, 포인터 주소 입력 | 포인터 쓰기가 버퍼 바로 뒤 칸을 건드리는지 (랩 123) |
| 안전 인덱서로 바꿔 보기 | `p[i]`를 잠깐 `scores[i]`로 | 범위를 넘기는지 예외로 확인 (랩 123) |

## 따라 해 보기: 랩 122 (피해 라벨)

1. 명령 인수에 번호를 넣고 **F5**. 콘솔에 아무것도 안 찍히고 프로그램이 사라집니다. `[FAIL]`도 없습니다.
2. `ToString`의 `=>` 줄에 **F9**, 다시 F5. 중단점이 멈출 때마다 **호출 스택 창**이 한 칸씩 길어집니다. `DamageLabel.ToString`이 계속 쌓입니다. → *처음 어긋난 줄*
3. 왜 `ToString`이 `ToString`을 부를까요? `$"{this} 피해"`에서 `{this}`가 `this.ToString()`을 부릅니다. 그게 바로 이 함수입니다.
4. 필요한 필드를 직접 쓰도록 고칩니다: `$"{Amount} 피해"`.
5. 채점기로 다른 금액(숨은 케이스)도 통과하는지 확인합니다. (참고: 랩 5의 `Gold` set 도 같은 모양의 자기 호출이었습니다. 호출 스택을 읽는 법은 두 랩이 같습니다.)

## SOLUTIONS.md에 들어갈 부분 (한국어)

## Lab 121 — 입력 크기로 `stackalloc` 해서 스택 오버플로
```
조사식 packet.Length:  20000000 (입력에서 온 값)
Checksum 첫 줄 F10:    프로그램이 사라짐. [FAIL]도 예외 창도 없음. 채점기 결과 CRASH (0xC00000FD)
진짜 원인:  stackalloc byte[n]은 스택에 n 바이트를 잡는다. 스택은 보통 1 MB로 고정이라
           수백만 바이트를 잡으면 StackOverflowException. 이 예외는 catch로 못 잡고 프로세스를 즉시 끝낸다.
```
**수정:** `stackalloc` 크기는 작고 고정된 상한(예: 1024 바이트) 안에서만 쓰고, 큰 입력은 힙(`ArrayPool<byte>`나 `new byte[n]`)으로 처리합니다. `const int StackCap = 1024;` 뒤 `packet.Length <= StackCap`일 때만 `stackalloc`, 아니면 `ArrayPool<byte>.Shared.Rent(...)` 후 `finally`에서 `Return`.
**교훈:** `stackalloc`의 크기는 **반드시 컴파일 시점에 아는 작은 상한** 안에 두세요. 입력·반복 횟수·재귀 깊이 중 어느 것이든 스택을 무제한으로 쓰면 오버플로입니다. 힙의 `OutOfMemoryException`은 그래도 잡을 수 있지만, 스택 오버플로는 잡을 수 없습니다.

## Lab 122 — `ToString`이 `$"{this}"`로 자기를 불러 무한 재귀
```
호출 스택:  DamageLabel.ToString → DamageLabel.ToString → … (수천 단계)
진짜 원인:  $"{this} 피해"의 {this}는 this.ToString()을 부른다. 그게 지금 실행 중인 ToString이다.
           무한 재귀로 스택을 다 쓰면 StackOverflowException으로 프로세스가 즉시 죽는다.
```
**수정:** `ToString`에서 그 객체 자신을 보간하지 말고 필드를 직접 씁니다: `$"{Amount} 피해"`.
**교훈:** `ToString`, `GetHashCode`, `Equals`, 연산자 오버로드, 속성 `get` 안에서 **자기 자신을 다시 부르지** 않도록 조심합니다. 흔한 형태: `ToString`에서 `$"{this}"`, `Equals`에서 `this == other`(→ `==` 연산자가 다시 `Equals`), `get`에서 같은 속성 대입. 랩 5(지갑)의 `set => Gold = ...`도 같은 뿌리입니다. 증상(프로그램이 조용히 사라짐)이 같으면 호출 스택부터 보세요.

## Lab 123 — `unsafe` 포인터 쓰기가 버퍼를 넘겨 옆 메모리를 덮어씀
```
중단점 p[i] = incoming[i], i == 4:  scores는 4칸(0~3)인데 p[4]에 씀
조사식 block[4] (가드):             쓰기 직후 0xC0FFEE → 50 으로 바뀜
진짜 원인:  포인터 p[i]는 경계 검사를 하지 않는다. p[4]는 버퍼 바로 뒤(가드 칸)를 덮어쓴다.
           같은 자리를 안전한 인덱서 scores[4]로 쓰면 IndexOutOfRangeException이 나서 바로 드러난다.
```
**수정:** 포인터로 쓸 때는 버퍼 용량으로 루프를 제한합니다: `for (int i = 0; i < incoming.Length && i < scores.Length; i++)`. 또는 포인터를 쓰지 말고 안전한 `Span` 인덱서를 쓰고, 넘치는 입력은 자르거나 거절하는 정책을 명시합니다.
**교훈:** `unsafe` 포인터, `Marshal`, `Unsafe.Add`로 메모리를 다룰 때는 경계 검사가 사라집니다. 한 칸만 넘겨도 예외가 아니라 **조용한 손상**이 되고, 그 피해는 전혀 다른 곳에서 나타나 추적이 어렵습니다. 성능을 위해 `unsafe`가 꼭 필요한 게 아니라면 `Span<T>`/`stackalloc`의 안전한 인덱서를 쓰세요.

### 참고: 네이티브 힙 손상 (랩 없음)
- `Marshal.AllocHGlobal` + `Marshal.Copy`로 네이티브 힙을 넘겨 쓰면 CLR 힙이나 다른 할당을 망가뜨릴 수 있습니다. 다만 그 결과(크래시인지, 조용한 손상인지, 어디가 깨지는지)가 런타임과 힙 상태에 따라 달라 **결정적이지 않아** 랩으로 넣지 않았습니다.
- `AllocHGlobal` 후 `FreeHGlobal`을 빼먹으면 네이티브 메모리 누수입니다. 이는 5부(리소스·메모리)의 누수 랩과 주제가 겹칩니다.

## 일본어판: 부 소개와 도구

(各ラボを該当する部の終わり近くに差し込みます。以下はラボ紹介の段落です。)

**スタックオーバーフロー (ラボ 121、122):** あるバグは例外を投げる代わりにプログラムを**丸ごと**消します。`[FAIL]` も例外ウィンドウも出ません。ほとんどの場合**スタックオーバーフロー**です: スタックに大きすぎるものを取ったか(`stackalloc`)、関数が自分自身を延々と呼んでいます(無限再帰)。この例外は `try/catch` で捕まえられません。デバッガーで F5 で動かして止まったら、**呼び出し履歴ウィンドウ**を見てください。同じ関数が何千回も積まれていれば無限再帰です。

**バッファオーバーラン (ラボ 123):** `unsafe` ポインターで配列・バッファに書くときは**範囲検査がありません。** 範囲を一マス越えただけでも例外が出ず、**隣のメモリを黙って上書きします。** だからバグがまったく見当違いの所(別の変数、別のオブジェクト)で出ます。同じ場所を安全なインデクサーで書けば `IndexOutOfRangeException` が出てすぐ分かる、という点と対比してください。

| ツール | 使い方 | いつ |
|---|---|---|
| 呼び出し履歴ウィンドウ | 止まったときデバッグ → ウィンドウ → 呼び出し履歴 | 同じ関数が延々と積まれているか (ラボ122) |
| ブレークポイントのヒットカウント | ブレークポイントを右クリック → ヒットカウント条件 | 再帰が何回回るか (ラボ122) |
| ウォッチに `stackalloc` のサイズ | `packet.Length` | スタックに取るサイズが入力から来るか (ラボ121) |
| メモリウィンドウ | デバッグ → ウィンドウ → メモリ、ポインターのアドレスを入力 | ポインターの書き込みがバッファのすぐ後ろを触るか (ラボ123) |
| 安全なインデクサーに置き換える | `p[i]` を一時的に `scores[i]` に | 範囲を越えているか例外で確認 (ラボ123) |

## 일본어판: 기록표 (SOLUTIONS)

### Lab 121 — 入力サイズで `stackalloc` してスタックオーバーフロー
```
ウォッチ packet.Length:  20000000 (入力から来た値)
Checksum の最初の行を F10:  プログラムが消える。[FAIL] も例外ウィンドウもない。採点結果 CRASH (0xC00000FD)
本当の原因:  stackalloc byte[n] はスタックに n バイトを取る。スタックはふつう 1 MB 固定なので、
            数百万バイトを取ると StackOverflowException。この例外は catch で捕まえられずプロセスを即座に終わらせる。
```
**修正:** `stackalloc` のサイズは小さく固定された上限(例: 1024 バイト)の中でだけ使い、大きい入力はヒープ(`ArrayPool<byte>` や `new byte[n]`)で処理します。`const int StackCap = 1024;` のあと `packet.Length <= StackCap` のときだけ `stackalloc`、そうでなければ `ArrayPool<byte>.Shared.Rent(...)` のあと `finally` で `Return`。
**教訓:** `stackalloc` のサイズは**必ずコンパイル時に分かる小さい上限**の中に収めてください。入力・反復回数・再帰の深さのいずれであれ、スタックを無制限に使えばオーバーフローです。ヒープの `OutOfMemoryException` はまだ捕まえられますが、スタックオーバーフローは捕まえられません。

### Lab 122 — `ToString` が `$"{this}"` で自分を呼び無限再帰
```
呼び出し履歴:  DamageLabel.ToString → DamageLabel.ToString → … (数千段)
本当の原因:  $"{this} 피해" の {this} は this.ToString() を呼ぶ。それが今実行中の ToString。
            無限再帰でスタックを使い切ると StackOverflowException でプロセスが即死する。
```
**修正:** `ToString` でそのオブジェクト自身を補間せず、フィールドを直接書きます: `$"{Amount} 피해"`。
**教訓:** `ToString`、`GetHashCode`、`Equals`、演算子オーバーロード、プロパティの `get` の中で**自分自身を再び呼ばない**よう気をつけます。よくある形: `ToString` で `$"{this}"`、`Equals` で `this == other`(→ `==` 演算子がまた `Equals` を呼ぶ)、`get` で同じプロパティへの代入。ラボ 5(財布)の `set => Gold = ...` も同じ根です。症状(プログラムが静かに消える)が同じなら呼び出し履歴から見てください。

### Lab 123 — `unsafe` ポインターの書き込みがバッファを越えて隣のメモリを上書き
```
ブレークポイント p[i] = incoming[i]、i == 4:  scores は 4 マス(0〜3)なのに p[4] に書く
ウォッチ block[4] (ガード):                  書き込み直後に 0xC0FFEE → 50 に変わる
本当の原因:  ポインター p[i] は範囲検査をしない。p[4] はバッファのすぐ後ろ(ガードのマス)を上書きする。
            同じ場所を安全なインデクサー scores[4] で書けば IndexOutOfRangeException が出てすぐ分かる。
```
**修正:** ポインターで書くときはバッファの容量でループを制限します: `for (int i = 0; i < incoming.Length && i < scores.Length; i++)`。またはポインターを使わず安全な `Span` のインデクサーを使い、あふれる入力は切り捨てるか拒否する方針を明示します。
**教訓:** `unsafe` ポインター、`Marshal`、`Unsafe.Add` でメモリを扱うと範囲検査が消えます。一マス越えただけでも例外ではなく**静かな破壊**になり、その被害はまったく別の所で現れて追跡が困難です。性能のために `unsafe` がどうしても必要なのでなければ、`Span<T>`/`stackalloc` の安全なインデクサーを使ってください。

### 参考: ネイティブヒープの破壊 (ラボなし)
- `Marshal.AllocHGlobal` + `Marshal.Copy` でネイティブヒープを越えて書くと、CLR のヒープや別の割り当てを壊しうります。ただしその結果(クラッシュか、静かな破壊か、どこが壊れるか)がランタイムとヒープの状態で変わり**決定的でない**ため、ラボには入れていません。
- `AllocHGlobal` のあと `FreeHGlobal` を忘れるとネイティブメモリのリークです。これは5部(リソース・メモリ)のリークのラボと主題が重なります。
