# N부: C# 언어 함정

이 부의 버그는 **코드를 소리 내어 읽으면 맞아 보입니다.** 연산자 우선순위, 값 형식의 복사, 람다의 변수 캡처, 문자열 인터닝, 부동소수점, 기본 반올림 규칙처럼 "언어가 그렇게 정의한" 동작이 읽는 사람의 기대와 다를 뿐입니다. 그래서 이 부에서는 **식을 쪼개서 조사식에 하나씩 넣어 보는 것**이 가장 강한 도구입니다. 한 줄 전체가 아니라 그 줄의 부분식이 각각 어떤 값과 형식을 가지는지 확인하세요.

## N부에서 쓰는 도구

## Lab 114 — `string.GetHashCode`를 저장했다가 다음 실행에서 비교
```
조사식 "화염구".GetHashCode():   실행할 때마다 다른 값 (예: 1182412346 → -503617214)
savedHashes:                     지난 세션 값(이 랩에서는 고정된 안정 해시로 대신함)
진짜 원인:  .NET Core 이후 문자열 해시는 프로세스마다 무작위 시드를 쓴다(해시 충돌 공격 방지).
           해시는 같은 프로세스 안의 Dictionary/HashSet을 위한 값이지, 저장하거나 보내는 식별자가 아니다.
```
**수정:** 해시가 아니라 **스킬 이름(또는 고정 Id)** 자체를 저장하고 비교합니다. 해시가 꼭 필요하면 FNV-1a, `XxHash64`(`System.IO.Hashing`), SHA-256 같은 **정의가 고정된 해시**를 직접 씁니다. 이 랩에서는 세이브 쪽이 안정 해시(`OldSessionHash`)로 저장돼 있으므로 비교도 `OldSessionHash(s)`로 하면 통과합니다.
**교훈:** `GetHashCode`의 계약은 "같은 프로세스에서, 같은 값이면 같은 해시"뿐입니다. 프로세스, 머신, .NET 버전을 넘어가는 순간 의미가 없습니다. `HashCode.Combine`도 같은 이유로 실행마다 다릅니다.

## Lab 115 — `a + b ?? 0`은 `(a + b) ?? 0`
```
조사식 baseDamage + comboBonus:           null   (형식 int?)
조사식 (baseDamage + comboBonus) ?? 0:     0
조사식 baseDamage + (comboBonus ?? 0):     80
진짜 원인:  ??는 +보다 우선순위가 낮다. int + int? 는 "리프트 연산자"로 int? 가 되고,
           한쪽이 null이면 결과도 null이다. 그 null에 ?? 0 이 붙어 기본 피해까지 0이 된다.
```
**수정:** `baseDamage + (comboBonus ?? 0)`, 또는 `comboBonus.GetValueOrDefault()`.
**교훈:** `??`, `?:`, `=>`처럼 우선순위가 낮은 연산자를 산술식 안에 쓸 때는 항상 괄호를 칩니다. nullable끼리의 `+ - * /`, `< >`는 null이 있으면 각각 null, `false`가 됩니다(`<`와 `>=`가 둘 다 `false`일 수 있음).

## Lab 116 — 범위 밖 enum 값이 `_ =>`로 기본 등급이 됨
```
등급 코드 9 → (Rarity)9 → 콘솔에 "9"
조사식 Enum.IsDefined((Rarity)9):  false
조사식 Weight((Rarity)9):           100 (Common과 같은 값)
진짜 원인:  enum은 이름 붙은 정수일 뿐이라 어떤 정수든 캐스트된다(예외 없음).
           switch의 _ => 100 이 "모르는 값"까지 Common 취급한다.
```
**수정:** 모르는 값에는 가중치를 주지 않습니다(`_ => 0`). 또는 받을 때 `Enum.IsDefined`로 걸러 건너뛰거나 `_ => throw new ArgumentOutOfRangeException(...)`.
**교훈:** 바깥에서 들어온 정수(패킷, 세이브, 설정)를 enum으로 바꿀 때는 범위 검사가 필요합니다. 비슷한 함정: `default(Rarity)`는 첫 멤버(0)라서 "지정 안 함"이 조용히 `Common`이 되므로, 0에는 `None`/`Unknown`을 두는 것이 안전합니다. `[Flags]` enum에서 `x.HasFlag(None)`은 항상 `true`입니다.

## Lab 117 — 값으로 넘긴 struct 커서는 바깥에서 진행되지 않음
```
TakeTurn 안 cursor._index:  매번 -1 → 0
Run 의 cursor._index:       계속 -1
진짜 원인:  TurnCursor는 struct라 TakeTurn(TurnCursor cursor)가 호출마다 복사본을 받는다.
           MoveNext는 복사본만 진행시키고 버려진다.
```
**수정:** `static string TakeTurn(ref TurnCursor cursor)`와 `TakeTurn(ref cursor)`, 또는 `TurnCursor`를 `class`로.
**교훈:** 상태를 가진 struct(열거자, 커서, 빌더)는 대입·매개변수·`readonly` 필드·`foreach` 반복 변수에서 복사됩니다. `List<T>.Enumerator`를 변수에 받아 다른 메서드로 넘기거나, `readonly` 필드에 둔 struct의 메서드를 부르는 경우(방어적 복사)도 같은 증상입니다.

## Lab 118 — 같은 문자열 리터럴에 lock 해서 서로 다른 시스템이 교착
```
병렬 스택:  스레드 A  AutoSave.Save → ManualResetEventSlim.Wait  (잠금을 쥔 채)
           스레드 B  Achievements.Tally → Monitor.Enter          (잠금을 기다림)
조사식 object.ReferenceEquals(save._lock, achievements._lock):  true
진짜 원인:  두 클래스가 각자 "bughunt-save-lock" 문자열을 잠금 객체로 썼다. 문자열 리터럴은
           인터닝되어 프로세스 전체에서 같은 객체이므로 두 잠금은 같은 모니터다.
```
**수정:** 각 클래스에 `private readonly object _lock = new();` (C# 13 이상이면 `System.Threading.Lock`).
**교훈:** 잠금 대상은 **그 목적만을 위해 만든 private 객체**여야 합니다. 문자열, `typeof(X)`, `this`, 박싱된 값, 바깥에 노출된 객체는 모르는 코드와 모니터를 공유할 수 있습니다. 또 "잠금을 쥔 채로 다른 작업을 기다리기"는 그 자체로 교착의 씨앗이므로 잠금 범위를 짧게 유지합니다.

## Lab 119 — `for` 변수를 캡처한 `Task.Run`
```
적중 시 로그 {i} (downloaded.Add(i)):  5, 5, 5, 5, 5
gate.Set() 줄에서 i:                   for를 다 돈 뒤라 이미 5(= pieces)
진짜 원인:  for의 i는 루프 전체에 하나뿐인 변수이고, 람다는 그 변수를 참조로 캡처한다.
           작업은 gate 때문에 루프가 끝난 뒤에 돌므로 모두 마지막 값(범위 밖)을 본다.
```
**수정:** 반복마다 복사본을 만듭니다(`int piece = i;` 후 `piece` 캡처). 또는 `foreach (int piece in Enumerable.Range(0, pieces))`, `Parallel.For`.
**교훈:** C# 5부터 `foreach`의 반복 변수는 반복마다 새로 만들어지지만, `for`의 변수는 아닙니다. 이 랩의 `gate`는 "작업이 늦게 시작하는" 상황을 결정적으로 만든 것이며, 실제로는 스레드 풀 상태에 따라 가끔만 틀립니다. 같은 뿌리의 다른 함정으로 `list.ForEach(async x => ...)`가 있습니다. `ForEach`는 `Action<T>`만 받으므로 람다가 `async void`가 되어 기다릴 수 없고 예외도 잡히지 않습니다(4부 비동기 예외 처리 참고).

## Lab 120 — 돈을 `double`로 더하고 `Math.Round`의 기본 반올림을 씀
```
조사식 sum (Total의 return):   0.30000000000000004
조사식 Math.Round(2.5m):        2
조사식 Math.Round(3.5m):        4
조사식 Math.Round(2.5m, MidpointRounding.AwayFromZero):  3
진짜 원인:  double은 0.1, 0.2를 정확히 담지 못해 합에 오차가 쌓인다.
           Math.Round의 기본은 MidpointRounding.ToEven(은행가 반올림)이라 2.5 → 2, 0.5 → 0.
```
**수정:** 합계를 `decimal`로 더합니다(`decimal sum = 0; sum += p;`). 세금은 `Math.Round(tax, MidpointRounding.AwayFromZero)`처럼 규칙을 명시합니다.
**교훈:** 돈, 수량, 점수처럼 10진수로 정확해야 하는 값은 `decimal` 또는 정수(원·센트 단위)로 다룹니다. 반올림 규칙은 도메인 결정이므로 항상 인자로 적습니다. `double` 합계를 `Math.Round(sum, 2)`로 감추는 수정은 이 랩의 숨은 케이스는 통과할 수 있지만, 값이 커지거나 연산이 길어지면 다시 어긋납니다. (참고: `(decimal)someDouble`은 유효숫자 15자리로 반올림해 변환하므로 오차를 가려 버립니다. 이 랩이 합계를 `double`로 비교하는 이유입니다.)

# N部: C# 言語の罠

この部のバグは**コードを声に出して読むと正しく見えます。** 演算子の優先順位、値型のコピー、ラムダの変数キャプチャ、文字列のインターン、浮動小数点、既定の丸め規則のように、「言語がそう定義した」動作が読む人の期待と違うだけです。そのためこの部では、**式を分解してウォッチに一つずつ入れてみること**が一番強い道具です。一行全体ではなく、その行の部分式がそれぞれどんな値と型を持つか確かめてください。

## 일본어판: 기록표 (SOLUTIONS)

### Lab 114 — `string.GetHashCode` を保存して次の実行で比べる
```
ウォッチ "화염구".GetHashCode():  実行ごとに違う値 (例: 1182412346 → -503617214)
savedHashes:                     前回のセッションの値(このラボでは固定の安定ハッシュで代用)
本当の原因:  .NET Core 以降、文字列のハッシュはプロセスごとにランダムなシードを使う(ハッシュ衝突攻撃の防止)。
            ハッシュは同じプロセス内の Dictionary/HashSet のための値で、保存したり送ったりする識別子ではない。
```
**修正:** ハッシュではなく**スキル名(または固定の Id)**そのものを保存して比べます。ハッシュがどうしても必要なら FNV-1a、`XxHash64`(`System.IO.Hashing`)、SHA-256 のような**定義が固定されたハッシュ**を自分で使います。このラボではセーブ側が安定ハッシュ(`OldSessionHash`)で保存されているので、比較も `OldSessionHash(s)` で行えば通ります。
**教訓:** `GetHashCode` の契約は「同じプロセスで、同じ値なら同じハッシュ」だけです。プロセス、マシン、.NET のバージョンを越えた瞬間に意味がなくなります。`HashCode.Combine` も同じ理由で実行ごとに違います。

### Lab 115 — `a + b ?? 0` は `(a + b) ?? 0`
```
ウォッチ baseDamage + comboBonus:          null   (型 int?)
ウォッチ (baseDamage + comboBonus) ?? 0:    0
ウォッチ baseDamage + (comboBonus ?? 0):    80
本当の原因:  ?? は + より優先順位が低い。int + int? は「リフト演算子」で int? になり、
            片方が null なら結果も null。その null に ?? 0 が付き、基本ダメージまで 0 になる。
```
**修正:** `baseDamage + (comboBonus ?? 0)`、または `comboBonus.GetValueOrDefault()`。
**教訓:** `??`、`?:`、`=>` のように優先順位の低い演算子を算術式の中で使うときは、必ず括弧を付けます。null 許容どうしの `+ - * /`、`< >` は null があるとそれぞれ null、`false` になります(`<` と `>=` が両方 `false` になりうる)。

### Lab 116 — 範囲外の enum 値が `_ =>` で既定の等級になる
```
等級コード 9 → (Rarity)9 → コンソールに "9"
ウォッチ Enum.IsDefined((Rarity)9):  false
ウォッチ Weight((Rarity)9):           100 (Common と同じ値)
本当の原因:  enum は名前の付いた整数にすぎず、どんな整数でもキャストできる(例外なし)。
            switch の _ => 100 が「知らない値」まで Common として扱う。
```
**修正:** 知らない値には重みを与えません(`_ => 0`)。または受け取るときに `Enum.IsDefined` で弾いてスキップするか、`_ => throw new ArgumentOutOfRangeException(...)`。
**教訓:** 外から来た整数(パケット、セーブ、設定)を enum に変えるときは範囲の検査が必要です。似た罠: `default(Rarity)` は最初のメンバー(0)なので「未指定」が黙って `Common` になります。0 には `None`/`Unknown` を置くのが安全です。`[Flags]` enum で `x.HasFlag(None)` は常に `true` です。

### Lab 117 — 値で渡した struct のカーソルは外で進まない
```
TakeTurn の中の cursor._index:  毎回 -1 → 0
Run の cursor._index:           ずっと -1
本当の原因:  TurnCursor は struct なので TakeTurn(TurnCursor cursor) は呼び出しごとにコピーを受け取る。
            MoveNext はコピーだけを進め、コピーは捨てられる。
```
**修正:** `static string TakeTurn(ref TurnCursor cursor)` と `TakeTurn(ref cursor)`、または `TurnCursor` を `class` に。
**教訓:** 状態を持つ struct(列挙子、カーソル、ビルダー)は代入・引数・`readonly` フィールド・`foreach` の反復変数でコピーされます。`List<T>.Enumerator` を変数に受けて別のメソッドに渡す場合や、`readonly` フィールドに置いた struct のメソッドを呼ぶ場合(防御的コピー)も同じ症状です。

### Lab 118 — 同じ文字列リテラルに lock して別々のシステムがデッドロック
```
並列スタック:  スレッド A  AutoSave.Save → ManualResetEventSlim.Wait  (ロックを握ったまま)
              スレッド B  Achievements.Tally → Monitor.Enter          (ロックを待つ)
ウォッチ object.ReferenceEquals(save._lock, achievements._lock):  true
本当の原因:  二つのクラスがそれぞれ "bughunt-save-lock" という文字列をロックオブジェクトにした。
            文字列リテラルはインターンされプロセス全体で同じオブジェクトなので、二つのロックは同じモニター。
```
**修正:** 各クラスに `private readonly object _lock = new();`(C# 13 以降なら `System.Threading.Lock`)。
**教訓:** ロックの対象は**その目的だけのために作った private オブジェクト**であるべきです。文字列、`typeof(X)`、`this`、ボックス化された値、外に公開されたオブジェクトは、知らないコードとモニターを共有しうります。また「ロックを握ったまま別の作業を待つ」こと自体がデッドロックの種なので、ロックの範囲を短く保ちます。

### Lab 119 — `for` 変数をキャプチャした `Task.Run`
```
ヒット時にログ {i} (downloaded.Add(i)):  5, 5, 5, 5, 5
gate.Set() の行での i:                  for を回し終えたあとなので、もう 5(= pieces)
本当の原因:  for の i はループ全体で一つだけの変数で、ラムダはその変数を参照でキャプチャする。
            タスクは gate のためループが終わったあとに動くので、すべて最後の値(範囲外)を見る。
```
**修正:** 反復ごとにコピーを作ります(`int piece = i;` のあと `piece` をキャプチャ)。または `foreach (int piece in Enumerable.Range(0, pieces))`、`Parallel.For`。
**教訓:** C# 5 から `foreach` の反復変数は反復ごとに新しく作られますが、`for` の変数は違います。このラボの `gate` は「タスクが遅れて始まる」状況を決定的にしたもので、実際にはスレッドプールの状態によって時々だけ間違います。同じ根の別の罠に `list.ForEach(async x => ...)` があります。`ForEach` は `Action<T>` しか受け取らないのでラムダが `async void` になり、待つことができず例外も捕まりません(4部の非同期の例外処理を参照)。

### Lab 120 — お金を `double` で足し、`Math.Round` の既定の丸めを使う
```
ウォッチ sum (Total の return):  0.30000000000000004
ウォッチ Math.Round(2.5m):        2
ウォッチ Math.Round(3.5m):        4
ウォッチ Math.Round(2.5m, MidpointRounding.AwayFromZero):  3
本当の原因:  double は 0.1、0.2 を正確に表せず、合計に誤差がたまる。
            Math.Round の既定は MidpointRounding.ToEven(銀行家の丸め)なので 2.5 → 2、0.5 → 0。
```
**修正:** 合計を `decimal` で足します(`decimal sum = 0; sum += p;`)。税は `Math.Round(tax, MidpointRounding.AwayFromZero)` のように規則を明示します。
**教訓:** お金、数量、スコアのように10進で正確であるべき値は `decimal` または整数(円・セント単位)で扱います。丸めの規則はドメインの決定なので、常に引数で書きます。`double` の合計を `Math.Round(sum, 2)` で隠す修正は、このラボの隠しケースは通るかもしれませんが、値が大きくなったり演算が長くなったりするとまたずれます。(参考: `(decimal)someDouble` は有効数字15桁に丸めて変換するので誤差を隠してしまいます。このラボが合計を `double` で比べる理由です。)
