# BugHunt — C# 버그 추적 실습

버그가 **일부러 심어진** 작은 게임 코드 모음입니다. [C++판 BugHunt](https://github.com/gusgh0157/BugHunt)의 C# 버전이고, 엔진(유니티 등)이 아니라 **C# 언어와 .NET 런타임 자체**에서 생기는 버그를 다룹니다.

- **1부: 예외와 스택 트레이스 (랩 1~7)**: 프로그램이 예외로 죽은 순간 **호출 스택**과 **스택 트레이스**를 거슬러 올라가 원인을 찾는 연습. 초보자는 여기부터 하세요.
- **2부: 흐름 추적 (랩 8~18, 연산자 랩 58~61)**: 프로그램은 **멀쩡히 끝나는데 결과가 틀리는** 버그들. 직접 중단점을 걸고 값을 확인하며 따라갑니다.
- **3부: 컨테이너와 컬렉션 (랩 19~25)**: 범위 밖 인덱스, `List<struct>` 복사본, 가변 키, 동시 수정, 불안정 정렬, `yield`와 지연 실행.
- **4부: 비동기와 동시성 (랩 26~35)**: `async`/`await`, `Task`, 스레드, 비동기 코드의 예외 처리(`catch ... when`, `ExceptionDispatchInfo`). 병렬 스택 창과 작업 창을 씁니다.
- **5부: 리소스와 메모리 (랩 36~38, 선택)**: `Dispose`, GC, 종료자. 메모리 스냅샷과 진단 도구를 씁니다.
- **6부: unsafe와 네이티브 메모리 (랩 39~44, 선택)**: 포인터, `stackalloc`, `fixed`, `GCHandle`, 네이티브 콜백, `ArrayPool`, 구조체 레이아웃. 메모리 창으로 주소와 바이트를 봅니다.
- **7부: 멈춤 - 무한루프와 데드락 (랩 45~50)**: 죽지도 않고 끝나지도 않는 버그. **모두 중단**, 병렬 스택, 스레드 창, `dotnet-stack`/`dotnet-dump`로 멈춘 순간을 봅니다.
- **8부: 성능 - 틀리지는 않는데 느리다 (랩 51~57)**: 결과는 맞는데 느린 코드. 핫 루프의 LINQ, 문자열 `+=`, 박싱, O(n²) 탐색, 반복 생성, 예외로 흐름 제어. 성능 프로파일러와 `dotnet-counters`로 **재서** 찾습니다.
- **챌린지 (C-1~C-3, B-1~B-8)**: 1~8부를 끝낸 뒤 푸는 시험. 힌트 없이 증상 한 줄만 줍니다. 여러 단계를 거쳐 퍼지는 버그(깊은 추적)와 범주를 숨긴 버그(블라인드). [챌린지](#챌린지) 참고.

> 2026-11 재배치: 기초에서 심화 순서로 부를 다시 짰습니다. 컨테이너가 3부(랩 19~25)로 올라오고, 4부(비동기)에 예외 처리 랩 33~35를 더했습니다. 예전 랩 19~25(비동기)는 26~32로, 예전 26~28(리소스)은 36~38로, 예전 29~40(unsafe, 멈춤)은 39~50으로, 예전 48~54(성능)는 51~57로 옮겨졌습니다.

어떤 버그를 어느 랩에서 다루는지는 [버그 범주별 커버리지](#버그-범주별-커버리지) 표에 모아 두었습니다. 아직 랩이 없는 대표 케이스도 "미포함"으로 적어 두었습니다.

> 코드를 눈으로 훑어 정답을 찾지 마세요. 1부는 **실행해서 죽게 만들고, 디버거가 멈춘 곳에서부터**, 2~8부는 **직접 멈춘 곳에서부터 값을 확인하며** 추적하세요.

## BugHunt 시리즈

같은 방식(일부러 심은 버그를 디버거로 추적)으로 만든 네 가지 판입니다.

| 판 | 다루는 버그 | 저장소 |
|---|---|---|
| C++ 콘솔 | 호출 스택, 메모리 오류, 크래시 없는 흐름 추적 (랩 35개) | [BugHunt](https://github.com/gusgh0157/BugHunt) |
| C# 콘솔 | 예외와 스택 트레이스, 흐름 추적, 비동기/동시성, 리소스와 메모리, unsafe/네이티브 메모리, 무한루프/데드락, 컨테이너, 성능, 챌린지 (랩 57개 + 챌린지 11개, 채점기) | [BugHuntCS](https://github.com/gusgh0157/BugHuntCS) **(지금 보는 저장소)** |
| 언리얼 엔진 | 크래시, 흐름 추적, 멀티플레이, 사운드, 이미지, 애니메이션 (랩 28개) | [BugHuntUE](https://github.com/gusgh0157/BugHuntUE) |
| 유니티 | 크래시/예외, 흐름 추적, 사운드, 이미지, 애니메이션 (랩 30개) | [BugHuntUnity](https://github.com/gusgh0157/BugHuntUnity) |

## 준비

필요한 것: **.NET 10 SDK**, **Visual Studio 2026** (또는 .NET 10을 지원하는 Visual Studio, ".NET 데스크톱 개발" 워크로드)

1. `BugHunt.sln`을 Visual Studio로 엽니다. (VS 2022 17.13 이상이면 `BugHunt.slnx`를 열어도 됩니다. Rider, VS Code 등 다른 IDE는 `.sln`을 쓰세요.)
   솔루션에는 채점기 프로젝트 `BugHunt.Grader`도 들어 있습니다. F5로 실행할 **시작 프로젝트는 `BugHunt`**입니다 (솔루션 탐색기에서 굵게 보이는 프로젝트).
2. 위쪽 도구 모음에서 구성을 **Debug**로 둡니다.
3. **F5**(디버깅 시작)로 실행 → 메뉴에서 랩 번호 입력.
   - 매번 같은 랩을 돌리려면: `BugHunt/Properties/launchSettings.json`의 `"commandLineArgs": ""`에 번호를 넣습니다 (예: `"1"`). 또는 솔루션 탐색기에서 BugHunt 우클릭 → 속성 → 디버그 → **디버그 시작 프로필 UI 열기** → **명령줄 인수**.
   - Ctrl+F5(디버깅하지 않고 시작)나 exe를 직접 실행하면 디버거가 붙지 않습니다. 콘솔에 스택 트레이스만 남고 끝납니다. 일부러 그렇게 보는 랩(5)도 있지만, 기본은 **F5**입니다.

명령줄에서:

```bash
dotnet run --project BugHunt -- 3
```

### 채점기

고친 뒤에는 채점기로 확인합니다. 저장소 폴더(이 README가 있는 곳)에서:

```bash
grade.bat
```

```bash
dotnet run --project BugHunt.Grader
```

둘은 같은 것입니다. 다른 폴더에서 `...grade.bat`을 불러도 채점기는 **자기가 들어 있는 저장소**를 채점합니다. 일부만 채점하려면 랩 번호를 붙입니다 (`grade.bat 45-50`, `grade.bat 1,5,39-44`). 챌린지는 `grade.bat C`(깊은 추적), `grade.bat B`(블라인드), `grade.bat C-1,B-3`처럼 코드로 고릅니다.

채점기(`BugHunt.Grader` 프로젝트)가 하는 일:

1. `BugHunt`를 **Debug와 Release로 새로 빌드**합니다. 빌드가 실패하면(경고도 오류입니다) 채점하지 않습니다.
2. 랩마다 `BugHunt.exe <번호>`를 **새 프로세스로** 띄웁니다. 그래서 한 랩이 죽거나(스택 오버플로, FailFast 포함) 멈춰도 다른 랩 채점에 영향이 없습니다.
3. 화면에 보이는 기본 입력으로 한 번, 그리고 **숨은 케이스**(무작위 시드로 만든 다른 입력)로 몇 번 더 돌립니다. 기대값을 코드에 박아 넣어 `[PASS]`만 맞춘 수정은 여기서 걸립니다. 숨은 케이스는 3부와 6~8부 랩, 챌린지에 있습니다 (1·2·4·5부는 기본 케이스만). 기본 케이스는 통과했는데 숨은 케이스에서 실패하면 상세 앞에 `증상은 사라졌지만 원인이 남아 있음`이 붙습니다.
4. JIT 최적화에 따라 결과가 달라질 수 있는 랩(39, 40, 42, 50, 챌린지 B-8)은 **Release로도** 돌립니다. 모든 실행이 통과해야 `PASS`입니다.
5. 콘솔에 표와 총점을, 저장소 루트에 `grade-report.json`을 남깁니다.

| 결과 | 뜻 |
|---|---|
| `PASS` | 모든 실행이 종료 코드 0, `[FAIL]` 없음, `[PASS]` 1개 이상 |
| `FAIL` | `[FAIL]`이 나왔거나 판정 출력이 없음 |
| `TIMEOUT` | 멈춤. 랩의 감시 타이머가 `[FAIL] 응답 없음`을 냈거나, 실행 한 번이 20초를 넘겨 채점기가 강제로 끝냄 |
| `CRASH` | 처리되지 않은 예외, 스택 오버플로, FailFast 등으로 프로세스가 죽음. 상세에 종료 코드가 나옵니다 |
| `SKIP` | 이 환경에서는 판정할 수 없음 (랩이 `[SKIP]`을 출력). 총점의 분모에서 빠집니다 |

처음에는 전부 `FAIL`, `CRASH`, `TIMEOUT`이 나오는 것이 정상입니다.

옵션:

| 옵션 | 뜻 |
|---|---|
| `--config Debug` / `--config Release` | 그 구성 하나로만 채점 |
| `--seed N` | 숨은 케이스 시드를 고정. 채점 결과 맨 아래에 나온 값을 넣으면 같은 입력으로 다시 채점합니다 |
| `--no-hidden` | 기본 케이스만 |
| `--no-build` | 빌드를 건너뜀 (이미 빌드된 것을 채점) |
| `--timeout MS` | 실행 한 번의 제한 시간 (기본 20000) |
| `--out 경로` | 보고서 위치 |

숨은 케이스 하나를 디버거로 다시 보려면, 실패 상세의 `seed` 값을 명령 인수에 같이 넣습니다: `"commandLineArgs": "46 --seed 123456"`.

#### grade-report.json 형식

BugHunt 네 판(C++, C#, 언리얼, 유니티)이 같은 형식을 씁니다.

```json
{
  "edition": "cs",
  "version": "1",
  "total": 68,
  "passed": 12,
  "labs": [
    { "id": 1, "title": "친구 프로필", "part": 1, "result": "PASS", "ms": 85, "detail": "" },
    { "id": 42, "title": "박자 콜백", "part": 6, "result": "CRASH", "ms": 152,
      "detail": "[Debug] 0x80131623 Process terminated. A callback was made on a garbage collected delegate ..." },
    { "id": 48, "title": "동시 거래", "part": 7, "result": "TIMEOUT", "ms": 2075,
      "detail": "응답 없음 (2000 ms 초과): 동시 거래" }
  ]
}
```

| 필드 | 형식 | 뜻 |
|---|---|---|
| `edition` | 문자열 | 판 이름. 이 저장소는 `"cs"` |
| `version` | 문자열 | 보고서 **형식**의 버전 (`"1"`) |
| `total` | 정수 | 채점한 랩 수 (SKIP 포함) |
| `passed` | 정수 | `PASS` 수 |
| `labs[].id` | 정수 | 랩 번호. 챌린지는 `C-n`이 `100+n`, `B-n`이 `200+n` (예: C-1은 101, B-3은 203) |
| `labs[].title` | 문자열 | 랩 이름 |
| `labs[].part` | 정수 | 부 번호 (1~8). 챌린지는 `9` |
| `labs[].result` | 문자열 | `PASS`, `FAIL`, `TIMEOUT`, `CRASH`, `SKIP` 중 하나 |
| `labs[].ms` | 정수 | 걸린 시간 (그 랩의 모든 실행을 합친 밀리초) |
| `labs[].detail` | 문자열 | 실패 이유 한 줄. `PASS`면 빈 문자열. 숨은 케이스나 Release에서 실패했으면 앞에 `[Release, 숨은 케이스 seed N]`처럼 붙음. 숨은 케이스에서만 실패했으면 그 앞에 `증상은 사라졌지만 원인이 남아 있음`이 더 붙음 |

파일은 UTF-8(BOM 없음)이고 채점기의 종료 코드는 만점이면 0, 아니면 1, 빌드 실패 등으로 채점을 못 하면 2입니다. CI에서 쓸 수 있습니다.

### 경고 정책

`BugHunt.csproj`는 **경고를 오류로 취급**합니다(`TreatWarningsAsErrors`). 그래서 빌드는 항상 경고 0개입니다.
그런데 현실의 코드처럼, 이 저장소에도 누군가 경고를 **꺼 두거나 눌러 둔** 곳이 있습니다 (`!`, `_ =`, `NoWarn`). 그 자리가 버그의 단서인 랩도 있습니다. 빌드 출력이 깨끗하다고 코드가 안전한 것은 아닙니다.

# 1부: 예외와 스택 트레이스

## 호출 스택과 스택 트레이스

함수가 함수를 부르면, 런타임은 "누가 나를 불렀는지"를 차곡차곡 쌓아 둡니다. 그 더미가 **호출 스택(Call Stack)**입니다.
예외가 던져지면 .NET은 그 순간의 호출 스택을 문자열로 찍어 예외 안에 넣어 둡니다. 그것이 **스택 트레이스(StackTrace)**입니다.

디버거 없이(Ctrl+F5) 랩 1을 실행하면 콘솔에 이렇게 남습니다.

```
Unhandled exception. System.NullReferenceException: Object reference not set to an instance of an object.
   at BugHunt.Lab01.PrintPlayer(Player player) in F:\...\Lab01_Profile.cs:line 34    ← 맨 위: 예외가 난 곳
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41      ← PrintPlayer를 부른 곳
   at BugHunt.Lab01.OpenFriendList() in F:\...\Lab01_Profile.cs:line 48
   at BugHunt.Lab01.Run() in F:\...\Lab01_Profile.cs:line 53
   at BugHunt.Program.Main(String[] args) in F:\...\Program.cs:line 98                ← 맨 아래: 프로그램의 시작
```

**위에서 아래로 읽으면 "누가 나를 불렀나"**, **아래에서 위로 읽으면 "프로그램이 여기까지 어떻게 왔나"**입니다.

스택 트레이스의 한 줄은 이렇게 생겼습니다.

```
   at BugHunt.Lab01.ShowProfile(String name) in F:\...\Lab01_Profile.cs:line 41
      └ 네임스페이스.클래스.메서드 ┘└ 매개변수 ┘    └──── 소스 파일 ────┘      └ 줄 ┘
```

자주 보이는 이상한 이름들:

| 스택에 보이는 이름 | 뜻 |
|---|---|
| `get_Gold`, `set_Gold` | `Gold` 속성의 get/set 접근자 |
| `<Run>b__0_0`, `<BindHotkeys>b__3_0` | 람다 (괄호 안이 람다를 품은 메서드) |
| `<>c__DisplayClass3_0` | 람다가 캡처한 변수를 담는 컴파일러 생성 클래스 |
| `<SaveAsync>d__1.MoveNext()` | async 메서드의 상태 기계. `MoveNext`가 메서드 본문입니다 |
| `--- End of stack trace from previous location ---` | 예외가 다른 곳(다른 스레드, await)에서 다시 던져진 경계 |
| `Repeat 12345 times:` | 같은 프레임이 반복됨. 스택 오버플로일 때 런타임이 접어서 보여 줍니다 |

## 디버거 창 사용법

| 하고 싶은 것 | 방법 |
|---|---|
| 호출 스택 창 | 디버깅 중 **Ctrl+Alt+C** |
| 지역 창 | **Alt+4** |
| 다른 프레임으로 이동 | 호출 스택 창에서 줄을 **더블클릭** → 코드 창이 그 함수의 "호출한 줄"(초록 화살표)로 이동하고, 지역 창이 **그 함수의 변수**로 바뀜 |
| 예외 도우미 | 예외로 멈췄을 때 뜨는 말풍선. **세부 정보 보기**, **내부 예외 보기**, "`player`이(가) null"처럼 원인 변수까지 알려 줌 |
| 지금 예외 객체 보기 | 조사식/즉시 창에 **`$exception`** |
| 예외 설정 창 | **Ctrl+Alt+E**. `Common Language Runtime Exceptions` 아래 예외를 체크하면 **처음 던져진 순간(first chance)** 멈춤. 누가 catch 하든 상관없이 |
| 외부 코드 보기 | 호출 스택 창 우클릭 → **외부 코드 표시** |
| 내 코드만 | 도구 → 옵션 → 디버깅 → 일반 → **내 코드만 사용**. 켜져 있으면(기본) .NET 내부 프레임이 `[외부 코드]` 한 줄로 접히고, 예외도 "내 코드에서 처리되지 않은" 순간에 멈춤 |

## 디버거가 멈추는 모습

| 모습 | 의미 | 할 일 |
|---|---|---|
| 예외 도우미: "처리되지 않은 예외" | 아무도 catch 하지 않았다. 던져진 줄에서 멈춤 | 호출 스택 창, 지역 창 |
| 예외 도우미: "사용자가 처리하지 않은 예외" | 내 코드 밖(.NET 내부, 스레드 풀)으로 빠져나가기 직전 | 호출 스택, **스레드 창** |
| 멈추지 않고 결과만 틀림 | 예외가 어딘가에서 catch 되었거나, 애초에 예외가 아닌 버그 | 예외 설정 창으로 first chance 중단, 또는 2부 방식 |
| 프로세스가 통째로 사라짐 | 스택 오버플로. try/catch로 못 잡는다 | 디버거로 다시 실행 (랩 5) |

## 추적 4단계 (1부 공통)

1. **어디서 멈췄나?** 호출 스택에서 **내 코드가 나오는 첫 줄**을 찾는다.
2. **무엇이 이상한가?** 예외 메시지와 그 프레임의 지역 창에서 이상한 값(null, 엉뚱한 키, 엉뚱한 형식...)을 찾는다.
3. **그 값은 어디서 왔나?** 한 칸 **아래** 프레임(= 나를 부른 함수)을 더블클릭해서, 그 값을 넘겨준 곳을 본다. 출처가 나올 때까지 반복한다.
4. **진짜 원인은?** 멈춘 곳이 아니라 **이상한 값이 처음 만들어진 곳**을 고친다.

> 💡 핵심: **죽은 곳 ≠ 잘못한 곳**인 경우가 대부분입니다.

```
기록표 (1부용)
멈춘 함수:              
이상한 값:              
그 값이 온 프레임:       
진짜 원인:              
수정:                   
```

# 2부: 흐름 추적 (크래시 없음)

1부에서는 프로그램이 죽어 주었습니다. 실무 버그의 대부분은 그렇지 않습니다. 프로그램은 끝까지 잘 돌고, **값 하나가 틀릴 뿐**입니다. 이때는 **내가 직접 멈추고, 직접 따라가야** 합니다.

> 2부부터는 **Debug** 구성에서 하세요. Release는 최적화 때문에 줄이 건너뛰어지거나 변수가 "최적화되었습니다"로 보일 수 있습니다.

## 흐름 추적 4단계 (2부 공통)

1. **기대를 먼저 적는다.** "이 줄이 끝나면 `Current`는 70이어야 한다"처럼, 따라가기 전에 각 단계의 기대값을 정한다.
2. **틀린 결과에서 가장 가까운 곳부터 멈춘다.** [FAIL]이 난 값을 만드는 함수 입구에 중단점을 건다.
3. **기대와 처음 달라지는 줄을 찾는다.** F10으로 넘기며 값을 확인한다. 달라진 줄이 함수 호출이면 그 안으로(F11) 들어간다.
4. **"처음 달라진 곳"을 고친다.** 그 뒤의 틀린 값들은 대부분 그 결과일 뿐이다.

```

틀린 결과:              
멈춘 위치:              
기대값 → 실제값:         
처음 어긋난 줄:          
진짜 원인:              
수정:                   
```

# 4부: 비동기와 동시성

비동기 버그는 **호출 스택이 거짓말을 하는 것처럼** 보입니다. `await` 뒤의 코드는 원래 부른 함수 위가 아니라, 나중에 다른 스레드(또는 같은 스레드의 다음 차례)에서 이어서 실행되기 때문입니다.
그래서 4부에서는 "지금 누가 무엇을 기다리고 있나"를 보여 주는 창들을 씁니다.

## 콘솔에는 "메인 스레드"가 없다

WinForms·WPF의 UI 스레드나 게임 엔진의 메인 스레드에는 **SynchronizationContext**가 있습니다. 그 스레드에서 `await`하면, 기다림이 끝난 뒤 **다시 그 스레드로 돌아와서** 나머지를 실행합니다.
콘솔 앱에는 이것이 없어서, `await` 뒤의 코드는 스레드 풀의 아무 스레드에서나 이어집니다. 그래서 `.Result` 데드락 같은 유명한 버그가 콘솔에서는 **재현되지 않습니다**.

이 실습은 `Labs/Part4_Async/MainThread.cs`에 작은 게임 루프를 만들어 둡니다. 일을 큐에 받아 **스레드 하나에서만** 차례로 실행하고, 자신을 SynchronizationContext로 등록합니다. 랩 27과 31은 이 "메인 스레드" 위에서 돕니다. 이 파일에는 버그가 없습니다.

# 5부: 리소스와 메모리 (선택)

.NET에는 GC가 있어서 `delete`를 안 해도 됩니다. 대신 **"언제" 정리되는지 내가 정할 수 없습니다.** 파일 핸들, GPU 메모리처럼 정해진 순간에 돌려줘야 하는 자원과, GC가 "아직 쓰는 중"이라고 착각하게 만드는 참조가 5부의 주제입니다.

## 5부에서 쓰는 도구

|---|---|---|
| 진단 도구 창 | 디버깅 중 **Ctrl+Alt+F2** → 메모리 사용량 탭 | 메모리 그래프, GC 표시(노란 깃발) |

# 6부: unsafe와 네이티브 메모리 (선택)

C#에도 포인터가 있습니다. `unsafe`, `stackalloc`, `fixed`, `GCHandle`, 함수 포인터, `Span`과 `ArrayPool`을 쓰면 C++처럼 메모리를 직접 다룰 수 있고, 그만큼 **C++과 같은 버그**도 생깁니다. 다른 점은 그 메모리 밑에서 **GC가 객체를 옮기고 수거한다**는 것입니다.

> 이 프로젝트는 `BugHunt.csproj`에서 `AllowUnsafeBlocks`를 켜 두었습니다.

## 멈춤 추적 4단계 (7부 공통)

1. **멈춘 순간에 들어간다.** 모두 중단, 또는 프로세스에 연결, 또는 dotnet-stack/dump.
2. **누가 일하고 누가 기다리나?** 스레드 창과 병렬 스택에서 내 코드가 맨 위 근처에 있는 스레드를 찾는다. CPU를 쓰면서 도는 중(무한루프)인지, `Wait`/`Monitor.Enter`/`WaitAsync`에서 기다리는 중(데드락)인지 구분한다.

# 8부: 성능 - 틀리지는 않는데 느리다

8부의 랩은 **결과가 모두 맞습니다.** 대신 쓰레기(할당)를 많이 만들거나, 같은 일을 쓸데없이 반복하거나, 예외를 흐름 제어에 씁니다. 게임에서는 프레임이 끊기고, 서버에서는 CPU와 GC가 치솟습니다. 중단점으로는 잘 안 보이고, **측정해야** 보입니다.

판정은 실행 시간이 아니라 **측정값**으로 합니다. PC가 바쁘면 시간은 흔들리지만 할당 바이트와 연산 횟수는 흔들리지 않기 때문입니다.

| 측정값 | 재는 법 |
|---|---|
| 할당 바이트 | `GC.GetAllocatedBytesForCurrentThread()`를 앞뒤로 재서 뺀다 (`LabKit.Measure`) |
| 비교 횟수 | `IEquatable<T>.Equals` 안에서 센다 (랩 54) |
| 던져진 예외 수 | `AppDomain.CurrentDomain.FirstChanceException`에서 센다 (랩 57) |

출력에 걸린 시간(ms)도 찍히지만 참고용입니다. 각 랩은 측정 전에 한 번 미리 돌려서 JIT 컴파일 같은 첫 실행 비용을 뺍니다.

| ↳ .NET 개체 할당 추적 | 체크하고 시작 → 할당 탭에서 형식별 개수, 역방향 호출 스택 | **누가 무엇을 얼마나** 만드나 (랩 51, 53, 55, 56) |

| 진단 도구 창 | 디버깅 중 자동으로 뜸(**Ctrl+Alt+F2**). GC 표시(노란 삼각형), 메모리 그래프 | 디버깅하면서 대충 보기. 측정은 프로파일러로 |
| `dotnet-counters` | `dotnet-counters monitor -n BugHunt --counters System.Runtime` | GC 횟수(gen0), 할당 속도, **초당 예외 수** |
| `dotnet-trace` | `dotnet-trace collect -n BugHunt` → `.nettrace`를 VS나 PerfView로 열기 | CPU 샘플, GC 이벤트. VS가 없는 서버에서 |
| 예외 설정 + 출력 창 | Ctrl+Alt+E에서 예외 체크 / 출력 창의 "예외 발생: ..." 줄 | 예외로 흐름 제어 (랩 57) |
| BenchmarkDotNet (선택) | 별도 프로젝트에 `[Benchmark]`, `[MemoryDiagnoser]` | 고치기 전후를 정확히 비교. 이 저장소에는 포함하지 않음 |

랩은 1초도 안 돼 끝나서 `dotnet-counters monitor`로 보기에는 짧습니다. 카운터를 보고 싶으면 랩의 반복 횟수(`count`, `frames` 등)를 잠시 100배쯤 늘려서 몇 초 동안 돌게 하세요.

## 성능 추적 4단계 (8부 공통)

1. **재기**: 무엇이 느린지 숫자로 적는다 (할당, 시간, GC 횟수, 예외 수). 추측으로 고치지 않는다.
2. **어디서**: 프로파일러로 가장 많이 할당하는 형식, 가장 오래 걸리는 함수를 찾는다. 내 코드가 아닌 내부 함수가 보이면 역방향 호출 스택으로 그것을 부른 **내 코드의 줄**까지 거슬러 간다.
3. **왜**: 그 줄이 무엇을 반복하는지 본다. 매번 새로 만드나(51, 55, 56)? 매번 통째로 복사하나(52)? 매번 처음부터 찾나(54)? 값 형식이 상자에 들어가나(53, 56)? 예외를 던지나(57)?
4. **다시 재기**: 고친 뒤 같은 방법으로 재서 줄었는지 확인한다. 결과가 그대로인지도(`[PASS]` 줄) 확인한다.

## 분석기와 컴파일러 경고

몇몇 랩의 버그는 컴파일러나 분석기가 **미리 알려 줄 수 있었던** 것입니다. 기본으로 켜진 것과, 직접 켜야 하는 것이 있습니다.

| 번호 | 내용 | 기본 | 관련 랩 |
|---|---|---|---|
| CS8600 계열 | nullable 경고 (null일 수 있는 값을 null 아님으로) | 켜짐 (`<Nullable>enable</Nullable>`) | 1 (`!`로 눌러 둠) |
| CS0649 | 필드에 아무것도 대입하지 않음 | 켜짐 | 5 (힌트 참고) |
| CA2200 | `throw ex;`는 스택 정보를 잃는다 | 켜짐 | 7 (`NoWarn`으로 꺼 둠) |
| CS4014 | await 하지 않은 Task 호출 | 켜짐 | 28 (`_ =`로 눌러 둠) |
| CA1806 | 메서드 반환값을 버림 (`string.Replace` 등) | **꺼짐**(제안) | 14 |
| CA1305 | 문화권(`IFormatProvider`)을 지정하지 않음 | **꺼짐** | 15 |
| CA2016 | 받은 CancellationToken을 넘기지 않음 | **꺼짐**(제안) | 32 |
| CA2000 | Dispose 하지 않고 범위를 벗어남 | **꺼짐** | 33 |

꺼진 규칙을 켜려면 `BugHunt` 폴더(또는 솔루션 폴더)에 `.editorconfig`를 만들고 아래처럼 씁니다. 버그를 고친 뒤에 켜면 경고가 사라지는 것을 확인할 수 있습니다.

```ini
[*.cs]
dotnet_diagnostic.CA1806.severity = warning
dotnet_diagnostic.CA1305.severity = warning
dotnet_diagnostic.CA2016.severity = warning
dotnet_diagnostic.CA2000.severity = warning
```

> 이 프로젝트는 경고를 오류로 취급하므로, 규칙을 켜면 해당 랩을 고치기 전까지 빌드가 안 됩니다. 그게 이 규칙들의 쓸모입니다.

## 자동 검증 결과

채점기(`grade.bat`)로 확인한 것 (Windows 11, .NET SDK 10.0.401):

**처음 만들 때** (지금 번호로 랩 1~18, 26~32, 36~38, 당시 번호 1~28. 옛 `BugHunt.exe grade`로)

- 버그 상태: 28개 모두 `FAIL` 또는 `CRASH` (Debug 3회, Release 1회)
- 정답 수정을 모두 적용: 28개 모두 `PASS` (Debug 3회, Release 1회)
- 정답 수정을 **하나씩만** 적용: 그 랩 하나만 `PASS`로 바뀜 (28가지 모두)
- 랩 30(경쟁 조건)은 버그 상태 단독 실행 30회 모두 `FAIL`, 수정 후 10회 모두 `PASS`
- 랩 27은 두 가지 수정(끝까지 async, `ConfigureAwait(false)`) 모두 `PASS`

**랩 19~25, 39~57과 새 채점기** (지금 번호)

- 정답 수정을 하나씩만 적용: 그 랩 하나만 `PASS`로 바뀜 (19~25, 39~57 모두)
- 랩 19~25, 39~44(unsafe)는 버그 상태로 Debug와 Release에서 기본 케이스 10번 + 숨은 케이스 10가지, 랩 45~50(멈춤)은 5번 + 5가지, 랩 51~57(성능)은 5번 + 10가지씩 단독 실행: 결과가 매번 같음. 크래시가 나는 랩(19, 24, 42)은 매번 같은 `CRASH`, 멈추는 랩은 매번 `TIMEOUT`. 숨은 케이스 중 버그 상태에서도 우연히 통과하는 입력이 랩 45에 하나 있었습니다(누적값이 목표를 정확히 밟는 경우). 기본 케이스는 항상 실패합니다
- 8부는 고친 뒤 측정값이 한도보다 훨씬 작습니다(Debug와 Release 모두 할당 0~2바이트, 예외 0개). 시간이 아니라 측정값으로 판정하므로 PC 부하에 흔들리지 않습니다
- 랩 50은 버그 상태에서 Debug는 `PASS`, Release는 `TIMEOUT` (의도한 차이). 채점기는 Release로도 돌리므로 `TIMEOUT`
- 기대값을 박아 넣은 "수정"(랩 45에서 10프레임을 그냥 그리게 함)은 기본 케이스는 통과하지만 숨은 케이스에서 `FAIL`
- 각 부별 커밋이 혼자서도 경고 0개로 빌드됨

**2026-11 재배치 뒤 전체** (4부 예외 처리 랩을 넣기 전. 번호는 지금 번호)

- 버그 상태 전체 채점: 0 / 54 (`CRASH` 10, `FAIL` 38, `TIMEOUT` 6)

**2부 연산자 랩 (임시 번호 58~61)**

- 버그 상태: 기본 케이스 + 숨은 케이스 8가지에서 Debug와 Release 모두 매번 `FAIL`. 정답 수정은 모두 `PASS`, 되돌리면 다시 `FAIL`. 하나씩만 고치면 그 랩만 `PASS`

- 전체: 버그 상태 0 / 72, 정답을 모두 적용하면 72 / 72 (기본 채점, `--config Release` 각각)

경쟁 조건(랩 30, 22)과 타이밍(랩 26~32, 48)은 PC 부하에 따라 결과가 달라질 수 있습니다. 버그 상태에서 `PASS`가 나오면 몇 번 더 실행해 보세요.

확인하지 못한 것: VS의 각 창(예외 도우미 문구, 병렬 스택 모양, 메모리 창, 메모리 스냅샷 화면)은 사람이 직접 띄워 보지 않았습니다. 버전에 따라 메뉴 이름이나 모양이 조금 다를 수 있습니다. `dotnet-stack`은 이 PC에 설치되어 있지 않아 실행해 보지 않았습니다.

dotnet-counters와 dotnet-dump(둘 다 10.0.750501)로 랩 37 절차를 실제로 해 봤습니다. 버그 상태에서는 `CombatLogWindow` 50개, `gcroot` 사슬이 `GameEvents.DamageDealt`로 이어지고, 고친 뒤에는 0개, LOH 0바이트였습니다. 랩 48의 `syncblk`/`clrstack -all` 출력도 실제로 뜬 덤프에서 가져왔습니다. 랩 36, 38과 6부는 명령줄 도구로 해 보지 않았습니다.
